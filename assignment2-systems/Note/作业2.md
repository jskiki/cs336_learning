**左上：前向时间花在哪些操作上**

每根柱子代表一个模型和上下文长度，总高度为 100%。

- 蓝色：全部矩阵乘法。
- 红色：注意力 softmax。
- 黄色：计算 scores 时的缩放、掩码等非矩阵操作。

**结论：序列越长，softmax、掩码等操作的占比越大。** 这里是前向 kernel 时间的占比，不是 GPU 利用率。

**右上：完整训练时间花在哪个阶段**

将训练 kernel 时间分为前向、反向、优化器更新和损失计算。

**结论：反向占比最大，约为 61%～69%。** 因此只加速前向，整个训练的提速会受到限制。

**左下：medium 的 softmax 内部耗时**

比较长度 1024 和 2048，将 softmax 分成除法、减去最大值、指数、求最大值与求和。

纵轴是**每遍前向跨 24 层累计的 kernel 时间**：从约 **14.40 ms** 增至 **54.60 ms**。

**结论：长度翻倍后，softmax 耗时接近四倍，而且减法、除法也占了不少时间。**

**右下：开启 Nsight 后，整体计时变化多少**

蓝色是仅前向，红色是完整训练。计算方式为：

\[ \frac{\text{采集时墙钟耗时}-\text{普通运行墙钟耗时}} {\text{普通运行墙钟耗时}}\times100\% \]

**结论：短模型对采集更敏感。** 但这些是不同次运行，差值同时包含运行波动，不能全部视为工具开销。

本次还发现 **Nsight 默认 backward GPU 投影漏掉 autograd 工作线程**：medium/1024 的默认值只有约 1.213 μs，但按 CUDA correlationId 跨线程重建后，完整反向 GPU 跨度约 211.439 ms/步，kernel 累计 208.223 ms/步。分析使用重建后的数据；所有 kernel 归属、数量与累计时间已验证。具体口径与原始未修正表见详细分析第 3 节。

仅前向长序列的本进程 GPU 活动间隙较小（medium/2048 约 0.68%、small/4096 约 0.52%），应优先研究实际 kernel 的成本；短模型采集更容易受工具与提交影响。这里的间隙不是系统级 GPU 空闲率，Memory 轨迹占比也不能代表 kernel 内部的显存流量。

优化方向：长上下文优先考虑注意力融合与分块以减少中间矩阵读写，同时覆盖反向；短模型检查大量小 kernel 与优化器提交。所有建议尚未实现，实际收益必须用普通端到端 benchmark 验证，不能把理论加速当作实测。

问题：（a）前向传播的总耗时是多少？是否与之前使用 Python 标准库测量的结果一致？

回答：Nsight 测得前向传播的平均 GPU 执行跨度为 **253.123 ms**，与相同配置下 Python 普通计时的 **253.026 ms** 接近。开启 Nsight 时，Python 测得的墙钟耗时为 **253.483 ms**，也与 GPU 跨度基本一致。

问题：（b）前向传播中，哪个 CUDA kernel 的累计 GPU 耗时最长？每次前向调用多少次？前向加反向时是否仍是它？

问题：（c）除矩阵乘法外，哪些 kernel 在前向传播中也占用了显著时间？

回答：softmax 中的归一化除法、减去最大值、指数及归约，以及注意力分数的缩放和掩码处理，都占用了显著时间。例如，softmax 的除法 kernel 每遍前向累计约 **20.389 ms**，占前向 kernel 总时间的 **8.10%**。

问题：（d）加入损失计算、反向传播和 AdamW 更新后，矩阵乘法与其他 kernel 的耗时占比如何变化？

回答：矩阵乘法占比从仅前向时的 **62.90%** 降至完整训练时的 **56.84%**，非矩阵操作占比相应增加。反向增加了逐元素运算、归约和梯度累加，AdamW 又增加了每步 **3066 次 kernel 调用**，累计执行约 **10.207 ms**。

问题：（e）注意力中的 softmax 与矩阵乘法耗时相比如何？是否符合它们的 FLOPs 差异？

回答：跨全部 24 层累计，softmax 每遍前向耗时约 **54.599 ms**，而 QK 与 PV 两次矩阵乘法合计约 **39.248 ms**，softmax 反而慢约 **1.39 倍**。虽然 softmax 的 FLOPs 明显更少，但多次大矩阵读写、归约和算子拆分增加了运行成本，因此耗时并不与 FLOPs 成正比。
