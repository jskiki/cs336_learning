**左上：前向时间花在哪些操作上**

每根柱子代表一个模型和上下文长度，总高度为 100%。

- 蓝色：全部矩阵乘法。

**结论：序列越长，softmax、掩码等操作的占比越大。** 这里是前向 kernel 时间的占比，不是 GPU 利用率。

**右上：完整训练时间花在哪个阶段**

将训练 kernel 时间分为前向、反向、优化器更新和损失计算。

**结论：反向占比最大，约为 61%～69%。** 因此只加速前向，整个训练的提速会受到限制。

**左下：medium 的 softmax 内部耗时**

比较长度 1024 和 2048，将 softmax 分成除法、减去最大值、指数、求最大值与求和。

纵轴是**每遍前向跨 24 层累计的 kernel 时间**：从约 **14.40 ms** 增至 **54.60 ms**。

**结论：长度翻倍后，softmax 耗时接近四倍，而且减法、除法也占了不少时间。**

**右下：开启 Nsight 后，整体计时变化多少**

蓝色是仅前向，红色是完整训练。计算方式为：

\[ \frac{\text{采集时墙钟耗时}-\text{普通运行墙钟耗时}} {\text{普通运行墙钟耗时}}\times100\% \]

**结论：短模型对采集更敏感。** 但这些是不同次运行，差值同时包含运行波动，不能全部视为工具开销。

```python
import torch

s1 = torch.tensor(0, dtype=torch.float32)
for i in range(1000):
    s1 += torch.tensor(0.01, dtype=torch.float32)
print(s1)

s2 = torch.tensor(0, dtype=torch.float16)
for i in range(1000):
    s2 += torch.tensor(0.01, dtype=torch.float16)
print(s2)

s3 = torch.tensor(0, dtype=torch.float32)
for i in range(1000):
    s3 += torch.tensor(0.01, dtype=torch.float16)
print(s3)

s4 = torch.tensor(0, dtype=torch.float32)
for i in range(1000):
    x = torch.tensor(0.01, dtype=torch.float16)
    s4 += x.type(torch.float32)
print(s4)
```

这四段代码都执行了 **1000 次累加**。区别在于两件事：**`0.01` 以什么精度保存，以及累加过程以什么精度进行。**

| 情况   | `0.01` 的类型   | 累加器 `s` 的类型 | 结果      |
| ------ | --------------- | ----------------- | --------- |
| 第一段 | FP32            | FP32              | `10.0001` |
| 第二段 | FP16            | FP16              | `9.9531`  |
| 第三段 | FP16            | FP32              | `10.0021` |
| 第四段 | FP16，再转 FP32 | FP32              | `10.0021` |

**第一段：FP32 输入，FP32 累加**

```
s += torch.tensor(0.01, dtype=torch.float32)
```

FP32 不能精确表示 `0.01`，而每次加法也可能产生舍入。1000 次累加后，得到接近 10 的 `10.0001`。

**第二段：FP16 输入，FP16 累加**

```
s += torch.tensor(0.01, dtype=torch.float16)
```

不仅 `0.01` 被近似表示，**每次累加的结果还必须舍入回 FP16**，累计误差明显增大，最终得到 `9.9531`。

例如，FP16 在 `[8, 16)` 范围内，相邻数间隔为 `0.0078125`，所以加上约 `0.01` 后，实际保存的增量可能只有 `0.0078125`。

**第三段：FP16 输入，FP32 累加**

```
s += torch.tensor(0.01, dtype=torch.float16)
```

FP16 保存的 `0.01` 实际约为：

```
0.01000213623046875
```

加法使用 FP32 精度进行，因此这里主要保留的是**输入量化误差**：

\[ 1000\times0.01000213623046875 =10.00213623046875 \]

显示为 `10.0021`，比第二段准确得多。

**第四段：显式转成 FP32 后累加**

```
x = torch.tensor(0.01, dtype=torch.float16)
s += x.type(torch.float32)
```

它与第三段效果相同：第三段在加法中进行类型提升，第四段显式转换。**转换只能保留 FP16 已经存下来的近似值，不能恢复成精确的 `0.01`**，因此结果同样是 `10.0021`。

这个实验说明：**低精度输入配合高精度累加，可以显著减少累加过程中的误差，但无法消除输入在低精度表示时已经产生的误差。**

### 关于混合精度训练的理解

混合精度训练在一些适合降低精度的计算时会降低精度进行计算，以此来达到加速训练的效果，但是模型的参数保存还是以最开始的设置来保存的如float32，（中间的一些结果有的是以低精度保存的如bfloat16）

#### 关于显存的占用

启用混合精度训练后，显存的变化要看两方面

\[ \text{显存净变化} = \text{转换副本等额外开销} - \text{低精度激活节省的空间} \]

“转换副本等额外开销”：为了低精度计算，新增加的张量

低精度激活节省的空间”：中间结果使用更少的字节保存

1. **参数保持原有类型，是因为 autocast 不会永久修改参数的 dtype。** 保存模型时，按参数当时的 dtype 保存；不是保存操作强制使用 FP32。我们初始化为 FP32，所以保存的权重仍是 FP32。

2. **显存公式是简化分析，不是精确的峰值计算公式。** 建议写成：

   \[ \text{显存净变化} \approx \text{额外副本及临时张量占用} - \text{低精度激活节省的空间} \]

   实际还取决于张量同时存在多久、计算图保留哪些结果，以及峰值发生在哪个阶段。

每组预热 5 步、记录 2 步；推理使用 `eval()` 和 `no_grad()`，完整训练包含前向、损失、反向及我们实现的 AdamW 更新，逐步同步 GPU。BF16 组只开启 autocast，原始参数、参数梯度及 AdamW 的一阶/二阶状态仍为 FP32。

## 问题（b）：两个上下文长度在前向和完整训练中的峰值显存分别是多少？

回答：FP32 的测量结果如下。

| 上下文长度 | 仅前向推理峰值 / GiB | 完整训练峰值 / GiB |
| --- | ---: | ---: |
| 128 | 12.90432 | 51.54268 |
| 2048 | 19.39646 | OOM，无法给出完整步骤峰值 |

这里的“仅前向”是关闭梯度记录的推理，与前文保留计算图的 `--mode forward` 不同，不能直接复用前文的峰值。

**OOM 证据：** FP32 在第一次前向的 softmax 附近申请额外 2 GiB 时失败；补采失败前已达到约 176.15 GiB peak allocated。BF16 能完成第一次前向，但在反向申请额外 2 GiB 时失败，补采失败前约 173.68 GiB peak allocated；这两个值都是未完成执行的下界，不能填进成功峰值表。

原因是当前显式注意力实现会物化多个大小为 `(4,32,2048,2048)` 的张量，FP32 时每个就是 **2 GiB**，训练又需跨 32 层保留部分中间结果。BF16 的 softmax 等计算仍有 FP32 路径，还会保存低精度权重副本，因此并没有消除这次 OOM；本轮没有偷偷缩小 batch 或更换注意力实现。

## 问题（c）：BF16 混合精度是否显著改变峰值显存？

| 上下文长度 | FP32 推理 / GiB | BF16 推理 / GiB | FP32 完整训练 / GiB | BF16 完整训练 / GiB |
| --- | ---: | ---: | ---: | ---: |
| 128 | 12.90432 | 12.91408 | 51.54268 | 51.40601 |
| 2048 | 19.39646 | 17.27830 | OOM | OOM |

回答：L=128 时，BF16 推理峰值约 12.914 GiB，较 FP32 的 12.904 GiB 略高，而完整训练仅从 51.543 降到 51.406 GiB，下降约 **0.27%**，并不显著；L=2048 的推理从 19.396 降到 17.278 GiB，下降约 **10.92%**。短序列完整训练的峰值位于 AdamW 阶段，FP32 参数、梯度和优化器状态占据大部分显存，因此激活降精度未显著降低全步骤峰值；长序列推理的临时激活占比更高，节省更明显。两种精度的 L=2048 完整训练均 OOM，因此无法比较其完成训练时的峰值，更不能据此推断混合精度训练始终省显存。

## 问题（d）：残差流中一个 FP32 激活张量有多大？

## 问题（f）：一个 TransformerBlock 为反向保存多少内存？最大的五项是什么？梯度占多少？

回答：另采集 xl、L=128、batch=4、FP32 的完整训练，启用 `nsys --cuda-memory-usage=true`、PyTorch `emit_nvtx(record_shapes=True)` 及逐块标记；这个独立诊断关闭 CUDA allocator 缓存，使 Nsight 能看到真实 `cudaMalloc/cudaFree` 生命周期，且包含首次 AdamW 状态初始化，不拿它的总峰值或耗时替代上面的稳态结果。以第 16 层为例，按 storage 去重、排除原有参数与 RoPE 缓冲区后，为反向保存的非参数张量共 **174.222656 MiB**，其中 5 MiB 输入已在调用前存在，故新增保存张量为 **169.222656 MiB**；前向结束还留下 5 MiB 输出。最大的五个独立保存结果均为 **20 MiB**，分别来自 FFN 的 W1 投影、sigmoid、SiLU 乘法、W3 投影和 SwiGLU 门控乘法，各占保存张量总量的 **11.48%**，合计 **57.40%**。

| 五个最大的独立保存结果 | 大小 / MiB | 占 174.222656 MiB 的比例 |
| --- | ---: | ---: |
| `W1(x)`：FFN 第一条投影结果 | 20 | 11.48% |
| `sigmoid(W1(x))` | 20 | 11.48% |
| `W1(x) × sigmoid(W1(x))`：SiLU 结果 | 20 | 11.48% |
| `W3(x)`：FFN 另一条投影结果 | 20 | 11.48% |
| `SiLU(W1(x)) × W3(x)`：门控结果 | 20 | 11.48% |

# 3.2 激活检查点

## 检查点设置理论分析

**如果以完整的 TransformerBlock 为分组单位，理论上应每层单独设置一个 checkpoint。** 原因是：这里一层内部的残差远大于保存一个层输入的开销。

设：

- \(N=32\)：模型层数。
- \(k\)：每个 checkpoint 包裹的层数。
- \(C\)：一个检查点输入的大小。
- \(R\)：一层反向传播所需的残差大小。

不允许嵌套时，需要长期保存约 \(N/k\) 个检查点；反向传播时，还需要重算当前分组，临时保存约 \(k\) 层的残差。因此，峰值激活显存可以粗略建模为：

\[ M(k)\approx \underbrace{\frac{N}{k}C}_{\text{检查点输入}} +\underbrace{kR}_{\text{当前分组的残差}} \]

这里忽略了张量共享、梯度和临时工作空间等细节，因此这个式子用于判断趋势，不能代替实测。

对于题目中的 FP32 输入：

\[ C=4\times2048\times2560\times4\text{ bytes} =80\text{ MiB} \]

采用教材中对 `torch.compile` 融合后单层残差的示例测量值（并非下面本地实现的单层实测值）：

\[ R\approx3651.31\text{ MiB} \]

将 \(k\) 暂时视为连续变量，对 \(M(k)\) 求最小值：

\[ M'(k)=-\frac{NC}{k^2}+R=0 \]

得到：

\[ k^*=\sqrt{\frac{NC}{R}} =\sqrt{\frac{32\times80}{3651.31}} \approx0.84 \]

由于整层分组要求 \(k\ge1\)，所以应选择 **\(k=1\)**。用同一个粗略模型比较：

| 每组层数 \(k\) | 保存的检查点 | 当前分组残差 | 合计        |
| -------------- | ------------ | ------------ | ----------- |
| 1              | 2560 MiB     | 3651.31 MiB  | 约 6.07 GiB |
| 2              | 1280 MiB     | 7302.62 MiB  | 约 8.38 GiB |

从每组一层改成两层，虽然减少了约 **1.25 GiB** 的检查点存储，却增加了约 **3.57 GiB** 的残差存储，因此这个近似模型预测峰值反而升高；实际最优粒度仍需通过不同分组大小的实验验证。

## 逐层检查点与无检查点基线对比（2026-11-16）

配置：B200、FP32，XL（32 层、16 头、d_model=2560、d_ff=10240），batch=4、序列长度=2048、词表=10000。测量前向＋反向，不含优化器更新，未启用 compile 或混合精度。

逐层 checkpoint 使用 `use_reentrant=False`，无嵌套；预热 2 步、测量 3 步，预热后重置显存峰值统计。

| 方案 | 结果 | 峰值 allocated / GiB | 每步耗时 / ms（均值 ± 标准差） |
| --- | --- | ---: | ---: |
| 无 checkpoint | OOM | — | — |
| 每层一个 checkpoint | 成功 | **33.254** | **4546.840 ± 0.342** |

**逐层 checkpoint 通过反向重计算减少激活保存，使该配置从 OOM 变为可运行。** 对照组 OOM，无法计算精确的显存节省率或耗时增幅；尚未比较相邻块大小，因此本轮不证明最优分组粒度。

**1. 专家怎样放到不同 GPU？**

假设一个 MoE 层有 4 个专家，使用两张 GPU：

```
GPU 0：专家 E₀、E₁
GPU 1：专家 E₂、E₃
```

在这个基本配置中，每张卡保存自己负责专家的完整参数及相关训练状态，不需要保存其他专家的完整副本。

如果单个专家也很大，还可以结合 TP，将一个专家内部的矩阵计算继续拆分。[DeepSpeed 专家并行配置](https://www.deepspeed.ai/tutorials/mixture-of-experts/)

**2. 前向传播：token 去找专家**

假设两张卡最初各有一个 token，使用 Top-2 路由：

```
GPU 0 的 token A → 专家 E₀、E₂
GPU 1 的 token B → 专家 E₁、E₂
```

执行过程如下。

**第一步：路由。**

Router 根据 token 的隐藏向量，计算目标专家和对应权重。

**第二步：分发（Dispatch）。**

```
token A：
  发给 GPU 0 的 E₀，本地处理
  发给 GPU 1 的 E₂，跨卡发送

token B：
  发给 GPU 0 的 E₁，跨卡发送
  发给 GPU 1 的 E₂，本地处理
```

传输的主要是 token 的隐藏向量及必要的路由信息，而不是把专家权重搬到 token 所在的卡。

**第三步：专家计算。**

```
GPU 0：
  E₀ 处理 A
  E₁ 处理 B

GPU 1：
  E₂ 批量处理 A、B
  E₃ 本次没有任务
```

实际实现会把发往同一专家的 token 组织成批次，进行矩阵计算。

**第四步：返回并合并（Combine）。**

专家输出返回原来负责该 token 的位置，然后按路由权重组合：

\[ y_A=\alpha_0E_0(x_A)+\alpha_2E_2(x_A) \]\[ y_B=\beta_1E_1(x_B)+\beta_2E_2(x_B) \]

结果恢复为原本的 token 顺序，进入后续网络。

多卡分发和回收常使用 **All-to-All** 或专门优化的通信实现。**All-to-All 不意味着每个 token 都发给全部 GPU；token 只需要送往选中专家所在的位置。** [DeepSeek-V3 通信实现](https://arxiv.org/html/2412.19437v2)

**3. 反向传播怎么做？**

反向沿前向的数据路径返回：

```
token 原位置获得输出梯度
            ↓
根据路由权重，把梯度发给选中的专家
            ↓
各专家计算：
  ① 自己的参数梯度
  ② 对 token 输入的梯度贡献
            ↓
输入梯度贡献返回 token 原位置
            ↓
合并贡献，继续向前面的网络反向传播
```

同一个 token 经过多个专家，其输入梯度需要汇总各专家路径的贡献；完整反向还需要计入 Router 对该 token 的依赖所产生的梯度。

不同专家拥有不同参数，因此 **不能把 E₀ 的参数梯度与 E₂ 的参数梯度相加**。每个专家使用分配给自己的 token 贡献的梯度更新参数。

如果同一个专家还有数据并行副本，则需要在这些副本之间同步梯度。

**4. EP 与 TP、PP 有什么区别？**

| 方式     | 拆分什么                     | token 如何参与计算          |
| -------- | ---------------------------- | --------------------------- |
| **EP**   | 同一 MoE 层的不同专家        | 路由到少数被选中的专家      |
| **TP**   | 一个层或专家内部的矩阵计算   | 多张 GPU 合作完成同一个算子 |
| **PP**   | 模型的不同层                 | token 依次经过多个阶段      |
| **FSDP** | 参数、梯度、优化器状态的存储 | 按需收集当前模块参数后计算  |

EP 的特点是：**计算任务分配随 token 的路由结果动态变化**，不是固定让所有 token 经过全部专家。

**5. EP 的主要收益和瓶颈**

**收益是专家存储可以分散。** 增加专家数量时，可以用更多 GPU 容纳参数，而每个 token 仍只激活少数专家。

但运行效率主要受三个因素影响：

- **负载不均衡**：热门专家忙，其他专家空闲，整批计算可能被最忙的专家拖慢。
- **通信开销**：token 分发和结果返回需要搬运激活值，跨节点时成本尤其明显。
- **专家批次过小**：每个专家只收到少量 token 时，矩阵计算可能难以充分利用 GPU。

因此，实际系统通常结合负载均衡路由、专家放置、批量计算，以及通信计算重叠来提高效率。[DeepSeek-V3 的专家并行与调度设计](https://arxiv.org/html/2412.19437v2)

### 梯度计算与all_reduce异步

每个 rank 都有一份参数，也各自算出一份**本地梯度**。钩子只负责通知当前 rank「我的梯度准备好了」。**等其他 rank 参与同一次归约，是 all-reduce 自己负责的。**

`register_post_accumulate_grad_hook` 是**参数张量的方法**，接收一个参数 `hook`，也就是你想让 PyTorch 自动调用的函数。

```
handle = parameter.register_post_accumulate_grad_hook(on_grad_ready)
```

回调函数的签名是 `hook(param: torch.Tensor) -> None`。当 `backward()` 更新了这个参数的 `.grad`，PyTorch 就会调用 `on_grad_ready(parameter)`。所以回调里收到的是**参数本身**，用 `param.grad` 读取或原地修改梯度。注册时写 `on_grad_ready`，表示把函数交给 PyTorch，留到反向传播时调用。[PyTorch 文档](https://docs.pytorch.org/docs/stable/generated/torch.Tensor.register_post_accumulate_grad_hook.html)

常见用途有三种：

- **观察梯度**，比如记录梯度的形状或范数。
- **修改梯度**，比如用 `param.grad.mul_(0.5)` 把这个参数的梯度缩小一半。
- **发起 DDP 通信**，比如在回调里对 `param.grad` 调用 `dist.all_reduce(..., async_op=True)`，把返回的通信句柄保存起来。

在 DDP 类里，可以直接把**绑定方法**传进去：

```
handle = parameter.register_post_accumulate_grad_hook(self._on_grad_ready)
```

如果 `_on_grad_ready` 定义成 `def _on_grad_ready(self, param):`，Python 会自动绑定 `self`，PyTorch 只需要传入 `param`。这样回调既能访问 `param.grad`，也能把通信句柄存到 `self` 上。

注册一次后，后续每次反向传播只要更新了这个参数的 `.grad`，回调就会触发。需要取消时，调用注册返回的 `handle.remove()`。

前两种时间接近，主要是因为**展平减少了通信调用次数，但两种方式要归约的梯度总量相同**，而且展平本身也有开销。

| 指标       | 逐参数 all-reduce | 展平后一次 all-reduce | 降幅  |
| ---------- | ----------------- | --------------------- | ----- |
| 梯度同步   | 37.092 ms         | 35.893 ms             | 3.23% |
| 完整训练步 | 564.963 ms        | 561.013 ms            | 0.70% |

有三个原因：

1. **XL 的梯度数据本身很大。** 每张卡约有 34 亿个 FP32 梯度元素，合计约 **13.6 GB**。仅一个 `2560 × 10240` 的权重矩阵，其梯度就约有 **105 MB**。逐参数版虽然调用次数多，但其中不少调用处理的是大张量，合并调用主要省下的是每次发起通信的固定开销。
2. **展平增加了 GPU 内存读写。** `torch.cat` 要把原梯度拷进连续缓冲区，归约完成后，`copy_()` 又要把平均后的梯度写回各参数。我们的同步计时包含这两步，所以它们会抵消一部分合并通信带来的收益。
3. **梯度同步只占原来整步的 6.57%。** 两种方式都在反向结束后才同步，前向、反向和优化器更新仍占大部分时间。同步阶段只省下约 **1.2 ms**，整步改善自然有限。
