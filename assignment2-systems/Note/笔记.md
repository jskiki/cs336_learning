## NVTX

**NVTX 是 NVIDIA 提供的一套标注库/API**，全称是 **NVIDIA Tools Extension**。它让你给代码片段添加名字，方便性能分析工具识别。

在 CUDA 版 PyTorch 中，可以直接使用 `torch.cuda.nvtx` 接口，无需另外安装 Python 的 `nvtx` 包。

最常用的是 `with`：

```python
import torch.cuda.nvtx as nvtx

with nvtx.range("forward"):
    logits = model(inputs)
```

这里：

- 进入 `with` 时，开始一个名为 `forward` 的标注区间。
- 执行区间内的代码。
- 离开 `with` 时，结束该区间。

`nvtx.range` 也可以作为装饰器，标记整个函数。

**标签需要配合 Nsight Systems 才方便查看。** 在已安装 `nsys` 的 GPU 环境中，可以这样启动现有脚本：

```bash
uv run nsys profile \
  --trace=cuda,nvtx \
  --output=results/profile \
  -- python -m cs336_systems.benchmark --device cuda --mode train
```

之后打开生成的 `.nsys-rep` 报告，就能看到 `forward` 区间，以及由这段 CPU 代码发起的 GPU 活动。

| 工具或接口                 | 作用                           |
| -------------------------- | ------------------------------ |
| NVTX                       | 给代码片段添加标签             |
| Nsight Systems             | 采集执行信息，展示时间线和统计 |
| `torch.cuda.synchronize()` | 等待 GPU 完成任务              |



## `torch.autocast` 

的核心规则是：**执行到每个算子时，根据 PyTorch 预先定义的策略选择精度，而不是把整个模型统一转成低精度。**

例如：

```
with torch.autocast(device_type="cuda", dtype=torch.bfloat16):
    y = model(x)
```

这里的 `bfloat16` 指定了**适合低精度执行的算子使用什么类型**，并不代表所有操作都使用 BF16。

**1. 不同算子采用不同策略**

以 CUDA autocast 为例：

| 策略                     | 常见操作                                               | 行为                                |
| ------------------------ | ------------------------------------------------------ | ----------------------------------- |
| 使用指定的低精度         | `linear`、`matmul`、`mm`、`bmm`、卷积                  | 将适用的浮点输入转换为 FP16 或 BF16 |
| 使用 FP32                | `layer_norm`、`softmax`、`exp`、`sum`、`cross_entropy` | 将适用的输入提升为 FP32             |
| 按最宽输入类型执行       | `addcmul`、`tensordot` 等                              | 输入中有 FP32，就统一使用 FP32      |
| 没有专门的 autocast 规则 | 如普通 ReLU                                            | 按算子自身的类型规则处理输入        |

普通加法等操作本身也有类型提升规则，不需要 autocast 介入。[官方算子列表](https://docs.pytorch.org/docs/2.11/amp.html#cuda-op-specific-behavior)

**2. 模型参数本身仍然是 FP32**

假设权重原本是 FP32，执行线性层时，可以理解为：

```
原始 FP32 输入、FP32 权重
          ↓ 为本次计算转换
      BF16 输入、BF16 权重
          ↓ 矩阵乘法
         BF16 输出
```

**原始参数没有被永久改成 BF16**，后续遇到需要 FP32 的算子时，又可以使用 FP32 计算。因此通常不需要提前调用 `model.half()` 或 `model.bfloat16()`。[官方说明](https://docs.pytorch.org/docs/2.11/amp.html#autocasting)

**3. 精度可以在网络中来回变化**

以题目的 ToyModel 为例，在 CUDA FP16 autocast 下，典型的数据流是：

```
FP32 输入
   ↓ Linear
FP16
   ↓ ReLU
FP16
   ↓ LayerNorm
FP32
   ↓ Linear
FP16 logits
   ↓ 官方 cross_entropy（也在 autocast 区间内）
FP32 loss
```

退出 `with` 后，**已经生成的输出不会自动转回 FP32**。

**4. 有些写法不会触发自动转换**

以下情况尤其要注意：

- **原地操作**，例如 `exp_()`、`add_()`，不会经过 autocast 的自动转换。
- 使用 `out=...` 的操作不会经过自动转换。
- 显式传入 `dtype=...` 时，遵循你指定的类型。
- 整数、布尔类型及 FP64 不会被自动降成 FP16/BF16。[适用条件](https://docs.pytorch.org/docs/2.11/amp.html#op-eligibility)

所以，**我们自己写的 `softmax` 不会因为函数叫这个名字，就自动全部使用 FP32**；autocast 看的是它内部实际调用的 PyTorch 算子。例如，我们的 `exp_()` 是原地操作，其行为就不同于官方列出的 `exp()`。

**5. 反向传播与损失缩放是另外两件事**

通常把前向和损失计算放在 autocast 中，在区间外调用 `loss.backward()`；反向按对应前向运算确定的精度路径执行，原始 FP32 参数的 `.grad` 通常仍为 FP32。`autocast` 本身不做损失缩放，FP16 训练通常还会搭配 `GradScaler`。



LayerNorm 中均值与方差的归约计算容易积累舍入误差，减去均值及对较小方差求倒数平方根也可能使误差更明显，因此通常使用 FP32 计算这些部分。改用 BF16 后仍需要关注这些问题：它虽然具有与 FP32 相同的指数范围，但有效精度更低，不能消除舍入误差；CUDA autocast 对官方 `layer_norm` 仍采用 FP32 策略。





### `nullcontext()`

 是一个**什么也不做的上下文管理器**，让关闭混合精度时，也能使用同一段代码。

这句代码的意思是：

```python
with (
    torch.autocast(device_type=inputs.device.type, dtype=torch.bfloat16)
    if mixed_precision
    else nullcontext()
):
    logits = model(inputs)
```

- `mixed_precision=True`：进入 `autocast`，按混合精度规则计算。
- `mixed_precision=False`：进入 `nullcontext()`，直接按原有精度计算。

这样就不用为开启、关闭混合精度分别复制一份前向代码。

注意，`nullcontext()` **不会主动关闭外层的 autocast**；它只是没有额外操作。我们当前没有外层 autocast，因此关闭开关时就是原来的 FP32 路径。

### 什么是上下文管理器

上下文管理器是 Python 中用来管理“一段代码执行前后要做什么”的机制，通常配合 `with` 使用。

执行过程可以理解为：

```
进入 with：执行准备操作
    ↓
执行 with 内缩进的代码
    ↓
退出 with：执行收尾操作，即使中间出现异常也会处理退出
```

例如，打开文件：

```
with open("note.txt", "r") as f:
    text = f.read()
```

进入时打开文件，退出时自动关闭文件。

你现在遇到的几个例子也是同样的结构：

| 上下文管理器            | 进入时                 | 退出时           |
| ----------------------- | ---------------------- | ---------------- |
| `torch.autocast(...)`   | 启用指定的混合精度规则 | 恢复进入前的设置 |
| `torch.no_grad()`       | 关闭梯度记录           | 恢复进入前的设置 |
| `nvtx.range("forward")` | 标记区间开始           | 标记区间结束     |
| `nullcontext()`         | 不做额外操作           | 不做额外操作     |

所以，`with` 中的缩进范围，就是这些设置或资源管理规则生效的范围。

### nullcontext()` **不会主动关闭外层的 autocast**；它只是没有额外操作。我们当前没有外层 autocast，因此关闭开关时就是原来的 FP32 路径。

意思是：**`nullcontext()` 不会改变当前设置，外面是什么状态，里面就保持什么状态。**

我们当前的代码没有外层 autocast：

```
# 当前没有开启 autocast
with nullcontext():
    logits = model(inputs)  # 保持原来的 FP32 路径
```

但如果外面已经开启了 autocast：

```
with torch.autocast("cuda", dtype=torch.bfloat16):
    with nullcontext():
        logits = model(inputs)  # 外层 autocast 仍然生效
```

这里 `nullcontext()` 没有执行任何关闭操作，所以仍使用混合精度规则。

**你现在的代码没有第二种嵌套情况，因此直接理解成：开关打开用混合精度，关闭就保持原来的 FP32 即可。**





量化可以从几个不同维度分类。**这些分类能组合使用：INT4 是数值格式，PTQ 是量化时机，GPTQ 是具体算法，它们并不是互斥的方案。**

**1. 按什么时候量化：PTQ 与 QAT**

| 方式                  | 做法                                               | 特点                                     |
| --------------------- | -------------------------------------------------- | ---------------------------------------- |
| **PTQ：训练后量化**   | 模型训练完成后，再转换权重和适用的激活             | 通常不需要重新训练，部分方法需要校准数据 |
| **QAT：量化感知训练** | 训练或微调时模拟量化误差，结束后转换成实际量化模型 | 让权重提前适应低精度表示，但需要额外训练 |

QAT 中常见的“伪量化”会模拟舍入、截断等误差，**张量和计算本身仍可能是浮点精度**，不代表训练时已经获得实际的 INT4 存储节省。[PyTorch QAT 说明](https://docs.pytorch.org/ao/stable/api_reference/generated/torchao.quantization.qat.QATConfig.html)

**2. 按量化什么：权重、激活与缓存**

常见写法中的 **W 是权重，A 是激活，数字表示位数**：

| 写法              | 含义                                     |
| ----------------- | ---------------------------------------- |
| **W4A16**         | 4-bit 权重，16-bit 激活                  |
| **W8A16**         | 8-bit 权重，16-bit 激活                  |
| **W8A8**          | 权重和激活都是 8-bit                     |
| **KV Cache 量化** | 降低推理过程中保存的 Key、Value 缓存精度 |

只量化权重通常称为 **weight-only quantization**。这些写法没有完整说明具体数值格式、累加精度，也不意味着模型每一层都使用相同精度。[torchao 支持的组合](https://docs.pytorch.org/ao/stable/workflows/inference.html)

**3. 按数值表示：INT、FP 与码本**

| 格式           | 基本方式                                                     |
| -------------- | ------------------------------------------------------------ |
| **INT8、INT4** | 用低位整数表示，通常配合缩放系数和零点                       |
| **FP8**        | 8-bit 浮点数，例如 E4M3、E5M2，通常也需要缩放                |
| **FP4**        | 4-bit 浮点表示，依赖相应的低精度实现                         |
| **NF4**        | 16 个非均匀代表值组成的 4-bit 码本，针对近似正态分布的权重设计 |

所以，**“4-bit 模型”不一定是 INT4，也可能是 NF4 或 FP4**。[NF4 原论文](https://arxiv.org/abs/2305.14314)

MXFP8、NVFP4 等名称还包含特定的分块缩放规则，不仅仅指定每个数值占几位。[NVIDIA 说明](https://docs.nvidia.com/deeplearning/transformer-engine/examples/fp8_primer.html)

**4. 按量化参数的共享范围：量化粒度**

| 粒度                      | 缩放参数如何共享                                  |
| ------------------------- | ------------------------------------------------- |
| **Per-tensor**            | 整个张量共用一组                                  |
| **Per-channel**           | 每个通道单独一组，例如线性层的每个输出通道        |
| **Per-group / Per-block** | 将权重分组或分块，每组单独一组，例如每 128 个权重 |
| **Per-token**             | 每个 token 的激活向量单独一组                     |

更细的粒度通常能更好地适应不同位置的数值范围，但需要更多缩放信息和相应的 kernel 支持。[量化粒度说明](https://docs.pytorch.org/ao/stable/contributing/quantization_overview.html)

**5. 按映射和缩放参数的确定方式**

整数仿射量化通常近似表示为：

\[ \hat w=s(q-z) \]

- **对称量化**：围绕零对称映射；有符号整数量化中通常令零点 \(z=0\)。
- **非对称量化**：允许零点偏移，更灵活地覆盖偏向一侧的分布。
- **静态量化**：适用的缩放参数提前通过校准等方式确定。
- **动态量化**：运行时根据当前输入计算量化参数，常用于激活。

“动态”通常不是说每次重新量化整个模型，而是指某些张量的量化参数随输入变化。[PyTorch 原理说明](https://pytorch.org/blog/quantization-in-practice/)

**6. 常见具体方法：这些名字分别是什么**

| 名称            | 属于什么               | 核心思路                                                     |
| --------------- | ---------------------- | ------------------------------------------------------------ |
| **GPTQ**        | 训练后权重量化算法     | 利用近似二阶信息补偿量化误差。[论文](https://arxiv.org/abs/2210.17323) |
| **AWQ**         | 激活感知的权重量化方法 | 利用激活统计，通过通道缩放保护重要权重。[论文](https://arxiv.org/abs/2306.00978) |
| **SmoothQuant** | 权重与激活量化方法     | 用等价缩放缓解激活异常值问题，帮助实现 W8A8。[论文](https://arxiv.org/abs/2211.10438) |
| **QLoRA**       | 量化模型上的微调方法   | 冻结低位基础权重，训练额外的 LoRA 参数。[论文](https://arxiv.org/abs/2305.14314) |

例如，一个方案可以描述成：

> **训练后使用 GPTQ，将权重做成 INT4、每组 128 个权重共享量化参数，激活使用 BF16。**



## Kernel Fusion 

**Kernel fusion（内核融合）就是把原本由多个 GPU 内核分别执行的运算，合并到一个 GPU 内核里完成。**

这里的 **kernel** 是在 GPU 上执行的一段程序。以实现的RMSNorm 为例：

```
rms = torch.rsqrt(x.pow(2).mean(-1, keepdim=True) + eps)
normalized = x * rms
y = weight * normalized
```

在没有融合的情况下，平方、求均值、加法、开方倒数、乘法等运算可能分别启动 GPU kernel。每一步的中间结果通常需要写入 GPU 显存，供下一步读取：

```
读取 x → 平方 → 写入显存
读取平方结果 → 求均值 → 写入显存
读取均值 → 加 eps → 写入显存
……
```

融合以后，一个 kernel 可以接连完成多个步骤，把部分中间结果保留在寄存器或共享内存中，最后再写出结果：

```
读取输入 → 在 kernel 内完成多个步骤 → 写出结果
```

它主要带来两个好处：

- **减少 kernel 启动开销**：每次启动 GPU kernel 都有成本，小运算尤其容易受影响。
- **减少显存读写**：不必把每一步的中间结果都写入显存，再读回来。对于 RMSNorm 这种运算，显存访问往往是重要瓶颈。

与你刚才那段教材联系起来，还需要区分**执行时的中间结果**和**为反向传播保存的张量**。

普通 PyTorch 执行时，autograd 会分别考虑每个算子的反向传播需求，因此可能保存多个中间张量。使用 `torch.compile` 后，编译器可以联合优化前向和反向计算，只保存必要的信息，在反向传播时重新计算一些中间结果。因此，教材中的 RMSNorm 最后只保存了：

```
x       [4, 512, 2560]   输入
weight  [2560]           权重
rms     [4, 512, 1]      每个 token 的归一化因子
```

**不过，“autograd 把它作为一个整体处理”并不意味着底层一定只执行一个 GPU kernel。** 一个编译后的函数仍然可能包含多个 kernel；具体能融合多少，取决于运算结构和编译器。



## 三种操作

- **AllReduce：先归约，每张卡都拿到完整结果。**
- **AllGather：收集分片，每张卡都拿到全部数据。**
- **ReduceScatter：先归约，每张卡只拿到结果的一部分。**

我们用同一组数据比较，假设两张 GPU 分别持有：

```
GPU 0：[2,  6]
GPU 1：[4, 10]
```

**1. AllReduce：逐位置计算，再让每张卡得到完整结果**

以求和 `SUM` 为例：

```
逐位置求和：[2+4, 6+10] = [6, 16]

操作后：
GPU 0：[6, 16]
GPU 1：[6, 16]
```

“Reduce”指按指定规则归约，例如求和、取最大值；“All”表示所有参与者都得到结果。

**DDP 用它聚合梯度。** 若要平均梯度，还要配合除以进程数等归一化操作；`SUM` 本身只求和。

**2. AllGather：把各卡的数据收集起来，不做求和**

```
操作前：
GPU 0：[2,  6]
GPU 1：[4, 10]

操作后，两张卡都得到：
[[2, 6], [4, 10]]
```

按 rank 顺序拼接，可以看成：

```
GPU 0：[2, 6, 4, 10]
GPU 1：[2, 6, 4, 10]
```

**AllGather 不求平均，也不合并对应位置的数值。**

在 ZeRO-1、ZeRO-2 中，可以用它收集各卡更新好的参数分片；在 ZeRO-3 中，可以用它临时收集当前模块需要的参数。

**3. ReduceScatter：逐位置归约，再把结果拆开分配**

仍以求和为例：

```
先归约得到：[6, 16]

再分片：
GPU 0：[6]
GPU 1：[16]
```

注意：GPU 0 得到的 `6`，包含两张卡的贡献 `2+4`；GPU 1 得到的 `16`，也包含两张卡的贡献 `6+10`。

**ZeRO-2、ZeRO-3 可以用它聚合梯度，并让每张卡只保留自己负责的梯度分片。**

**4. 三者的关系**

| 操作          | 是否进行求和等计算 | 每卡最后拿到什么   |
| ------------- | ------------------ | ------------------ |
| AllReduce     | 是                 | 完整归约结果       |
| AllGather     | 否                 | 所有卡的原始数据   |
| ReduceScatter | 是                 | 归约结果的一个分片 |

## NVlink与NVswitch以及**InfiniBand** 

| 技术                    | 是什么                                       | 主要作用                                                |
| ----------------------- | -------------------------------------------- | ------------------------------------------------------- |
| **NVLink**              | NVIDIA 的高速互联技术，包含链路与协议        | 让 GPU 之间高速交换数据，某些平台也用于 CPU 与 GPU 互联 |
| **NVSwitch**            | 专门处理 NVLink 通信的交换芯片               | 将多个 GPU 连接成高带宽的交换网络                       |
| **InfiniBand，简称 IB** | 一套高性能网络技术，包括网卡、交换机、协议等 | 将服务器或机架连接起来，组成大规模集群                  |

两个 GPU 可以直接通过 NVLink 相连。但 GPU 数量增加后，如果每两个 GPU 都单独直连，端口和布线会变得复杂。

NVSwitch 提供交换能力：GPU 通过 NVLink 连接到 NVSwitch，再经由交换网络访问其他 GPU。因此，**GPU 之间能够互通，并不意味着每一对 GPU 都有一根独立的直连线**。

服务器内部的 GPU 通信走 NVLink/NVSwitch；跨服务器通信则通过 IB 网卡和 IB 交换机。配合 **GPUDirect RDMA（远程直接内存读写）**，网卡可以直接读写 GPU 显存，减少数据经过 CPU 内存中转的开销。



```
训练策略：          DDP、模型并行等
                        ↓
PyTorch 通信接口：  torch.distributed
                        ↓
通信后端：          NCCL（NVIDIA GPU 常用）
                        ↓
硬件互联：          NVLink / NVSwitch / PCIe / InfiniBand / 以太网
```

**1. 它的基本单位是进程**

典型的 GPU 分布式训练采用 **一个进程控制一张 GPU**，每个进程执行同一份 Python 脚本，根据自己的编号处理不同数据。

需要理解四个概念：

| 概念            | 含义                   | 两台机器、每台 4 张 GPU 的例子   |
| --------------- | ---------------------- | -------------------------------- |
| `world_size`    | 通信组中的进程总数     | 默认组中为 8                     |
| `rank`          | 进程在组内的编号       | 默认组中为 0～7                  |
| `local_rank`    | 进程在当前机器内的编号 | 每台机器分别为 0～3              |
| `process_group` | 参与一组通信的进程集合 | 可以是全部进程，也可以是部分进程 |

`rank` 是进程编号；在“一进程一卡”的约定下，才与 GPU 建立对应关系。通常使用 `local_rank` 选择当前机器上的 GPU。[torchrun 文档](https://docs.pytorch.org/docs/stable/elastic/run.html)

**2. 核心能力是进程之间的通信**

除了 `send`、`recv` 这样的点对点通信，更常见的是 **集合通信（collective）**，即一组进程共同参与的操作：

| 操作             | 含义                                             |
| ---------------- | ------------------------------------------------ |
| `broadcast`      | 一个进程把数据发给组内所有进程                   |
| `all_reduce`     | 对所有进程的数据执行求和等归约，每个进程得到结果 |
| `all_gather`     | 收集各进程的数据，每个进程都得到完整集合         |
| `reduce_scatter` | 归约后，把结果的不同分片交给不同进程             |
| `all_to_all`     | 各进程分别向其他进程交换数据分片                 |
| `barrier`        | 等待组内所有进程到达某个位置                     |

例如，三个进程各有一个数：

```
              rank 0    rank 1    rank 2
操作前：         1         2         3
all_reduce SUM
操作后：         6         6         6
```

这些都是 `torch.distributed` 提供的基础通信操作。[通信 API 文档](https://docs.pytorch.org/docs/stable/distributed.html)

**3. NCCL 是它调用的通信后端**

`torch.distributed` 提供统一接口，实际通信由后端执行：

- **NCCL**：NVIDIA GPU 训练的常用选择，支持单机多卡和多机多卡。
- **Gloo**：CPU 分布式计算的常用选择。

同一个 `dist.all_reduce()`，可以通过不同后端完成；NCCL 会利用 NVLink、NVSwitch、InfiniBand 等可用互联。因此，设置 `backend="nccl"` 并不等于指定使用 InfiniBand。[PyTorch 后端选择说明](https://docs.pytorch.org/docs/stable/distributed.html#which-backend-to-use)，[NCCL 硬件支持](https://developer.nvidia.com/nccl)

**4. 一个最小例子**

下面的程序在一台有 4 张 NVIDIA GPU 的机器上运行。保存为 `demo.py`：

```
import os
import torch
import torch.distributed as dist

local_rank = int(os.environ["LOCAL_RANK"])
torch.cuda.set_device(local_rank)

# torchrun 提供 rank、world_size 和初始化所需环境变量
dist.init_process_group(backend="nccl")

rank = dist.get_rank()
device = torch.device("cuda", local_rank)
x = torch.tensor([float(rank + 1)], device=device)

# 原地修改 x：所有进程的值相加，每个进程得到结果
dist.all_reduce(x, op=dist.ReduceOp.SUM)

print(f"rank={rank}, result={x.item()}")
dist.destroy_process_group()
```

启动：

```
torchrun --standalone --nproc-per-node=4 demo.py
```

`torchrun` 启动 4 个进程，每个进程执行整份脚本。初始值分别为 `1、2、3、4`，通信后每个进程都输出 `10`，打印顺序可能不同。[torchrun 使用说明](https://docs.pytorch.org/docs/stable/elastic/run.html)

**5. 它和 DDP 的关系**

`torch.distributed` 提供通信基础，**DDP（DistributedDataParallel）在此基础上实现数据并行训练**：

```
GPU 0：完整模型 + 数据分片 A → 计算梯度 ─┐
                                       ├→ 同步梯度 → 各自更新模型
GPU 1：完整模型 + 数据分片 B → 计算梯度 ─┘
```

DDP 会在反向传播过程中同步各模型副本的梯度，你通常无需手写梯度的 `all_reduce`。但 **DDP 不会自动切分输入数据**，通常需要搭配 `DistributedSampler`，让不同进程读取不同的数据分片。[DDP 官方文档](https://docs.pytorch.org/docs/stable/generated/torch.nn.parallel.DistributedDataParallel.html)

实际编程时尤其要注意：**同一通信组内的进程需要按一致顺序调用匹配的集合通信操作**。例如，只有 rank 0 调用 `all_reduce`，其他进程没有参与，就可能一直等待或超时。[分布式通信文档](https://docs.pytorch.org/docs/stable/distributed.html)

**1. 通信接口里的同步与异步**

假设所有进程都已经初始化，并且各自有一个张量 `x`。

同步调用是默认行为：

```
dist.all_reduce(x, async_op=False)

# 接下来使用归约结果
y = x * 2
```

异步调用会返回一个 `Work` 句柄，你可以把等待推迟：

```
work = dist.all_reduce(x, async_op=True)

# 可以先做与 x 无关的工作
z = other_tensor * 2

# 在需要 x 的结果前建立等待关系
work.wait()
y = x * 2
```

**异步期间不要读取或修改正在参与通信的 `x`，除非已经正确同步。** 对 CUDA 张量，以上结果使用假设在同一条 CUDA stream 上。



## DDP

**DDP（DistributedDataParallel）是 PyTorch 的分布式数据并行训练工具：每张 GPU 保存完整模型，处理不同数据，通过同步梯度共同训练。**

它建立在 `torch.distributed` 之上，可以用于单机多卡，也可以用于多机多卡。[DDP 官方文档](https://docs.pytorch.org/docs/stable/generated/torch.nn.parallel.DistributedDataParallel.html)

**1. 一次训练迭代发生了什么**

假设有 4 张 GPU，通常启动 4 个进程，每个进程控制一张卡：

```
rank 0 / GPU 0：完整模型 + 数据 A → 梯度 g₀ ─┐
rank 1 / GPU 1：完整模型 + 数据 B → 梯度 g₁ ─┤
rank 2 / GPU 2：完整模型 + 数据 C → 梯度 g₂ ─┤→ AllReduce，计算平均梯度
rank 3 / GPU 3：完整模型 + 数据 D → 梯度 g₃ ─┘
                                               ↓
                                   每个进程用平均梯度更新模型
```

默认情况下，各进程获得：

\[ \bar g = \frac{g_0+g_1+g_2+g_3}{4} \]

过程可以拆成四步：

1. **初始化**：DDP 默认同步模型初始参数，让各副本从相同状态开始。
2. **前向计算**：各 GPU 用自己的数据计算输出和 loss。
3. **反向传播**：各 GPU 计算本地梯度，DDP 自动同步、平均梯度。
4. **更新参数**：每个进程调用自己的 `optimizer.step()`。

**每个进程都执行参数更新。** 因为初始参数、同步后的梯度和优化器更新规则一致，模型参数得以保持一致。[DDP 工作原理](https://docs.pytorch.org/docs/stable/notes/ddp.html)

**2. 梯度同步发生在 `backward()` 过程中**

DDP 会把梯度组织成多个 **bucket（桶）**。一个桶的梯度准备好后，就可以启动异步 AllReduce，同时继续计算其他梯度：

```
反向计算： [后层梯度][中层梯度][前层梯度]
通信：             [桶 1 同步][桶 2 同步][桶 3 同步]
```

这就是前面提到的**通信与计算重叠**。DDP 负责安排同步依赖，普通训练代码不需要手写梯度的 `all_reduce()`，也不需要在每次更新前额外插入 `barrier()`。[DDP 设计说明](https://docs.pytorch.org/docs/stable/notes/ddp.html)

**3. DDP 负责同步梯度，数据需要另外划分**

如果所有进程读取完全相同的数据，就会重复计算。通常用 `DistributedSampler` 给各进程分配不同的数据索引：

```
sampler = DistributedSampler(dataset, shuffle=True)
loader = DataLoader(dataset, batch_size=32, sampler=sampler)

for epoch in range(epochs):
    sampler.set_epoch(epoch)
    # 遍历 loader，执行训练
```

`sampler.set_epoch(epoch)` 让每轮使用不同的打乱顺序。数据不能整除进程数时，采样器会根据设置补齐或丢弃部分索引。[DistributedSampler 文档](https://docs.pytorch.org/docs/stable/data.html#torch.utils.data.distributed.DistributedSampler)

这里的 `batch_size=32` 是**每个进程的 batch size**。若有 4 个进程、不做梯度累积，每次更新的全局 batch size 就是：

```
32 × 4 = 128
```

在每卡样本数相同、loss 按样本取平均等条件下，平均各卡梯度，对应于对这个全局 batch 求平均梯度。

**4. 代码里最关键的部分**

假设模型、数据集和损失函数已经定义，核心训练代码是：

```
import os
import torch
import torch.distributed as dist
from torch.nn.parallel import DistributedDataParallel as DDP
from torch.utils.data import DataLoader, DistributedSampler

local_rank = int(os.environ["LOCAL_RANK"])
torch.cuda.set_device(local_rank)
device = torch.device("cuda", local_rank)

dist.init_process_group("nccl")

model = DDP(model.to(device), device_ids=[local_rank])
optimizer = torch.optim.AdamW(model.parameters(), lr=1e-4)

sampler = DistributedSampler(dataset)
loader = DataLoader(dataset, batch_size=32, sampler=sampler)

for epoch in range(epochs):
    sampler.set_epoch(epoch)

    for inputs, targets in loader:
        inputs = inputs.to(device)
        targets = targets.to(device)

        optimizer.zero_grad()
        loss = loss_fn(model(inputs), targets)
        loss.backward()    # DDP 自动同步梯度
        optimizer.step()   # 每个进程更新自己的模型

dist.destroy_process_group()
```

通过下面的命令启动单机 4 卡训练：

```
torchrun --standalone --nproc-per-node=4 train.py
```

**5. DDP 能解决什么，限制在哪里**

DDP 适合**模型能放进单卡，希望用更多 GPU 提高训练吞吐量**的场景。

普通 DDP 下，每张卡仍保存完整的模型参数、梯度和优化器状态，所以增加 GPU 数量不会自动把显存合并起来。模型本身放不进单卡时，需要考虑参数分片或模型并行等方式。

它和前面几个组件的分工可以这样记：

| 组件                       | 负责什么                   |
| -------------------------- | -------------------------- |
| `torchrun`                 | 启动多个训练进程           |
| `DistributedSampler`       | 划分各进程读取的数据       |
| DDP                        | 管理模型副本之间的梯度同步 |
| `torch.distributed` / NCCL | 执行底层通信               |
| `optimizer`                | 在各进程中更新模型参数     |

另外，**DDP 默认不会把各进程的 loss 自动求平均**。rank 0 打印的 `loss.item()` 通常只是 rank 0 当前数据的 loss；要记录全局指标，需要另外做聚合。

## ZeRO

**ZeRO 的核心，是把分布式训练中重复保存的状态分给不同 GPU 管理，并在计算需要时通过通信取得数据。** 它保留数据并行的计算方式：不同 GPU 处理不同样本，但不再要求每张 GPU 长期保存完整的训练状态。

结合前面的讨论，理解 ZeRO 需要回答三个问题：**显存里存了什么、每张卡负责什么、什么时候通信。**

**1. 为什么训练一个模型，需要远多于权重本身的显存？**

训练显存主要包含：

\[ M_{\text{总}} =M_{\text{参数}}+M_{\text{梯度}}+M_{\text{优化器状态}} +M_{\text{激活值}}+M_{\text{临时缓冲}} \]

以一种经典的 **FP16 混合精度 Adam** 配置为例：

| 内容                        | 每个参数对应的存储量 |
| --------------------------- | -------------------- |
| FP16 模型参数               | 2 字节               |
| FP16 梯度                   | 2 字节               |
| FP32 主参数，用于高精度更新 | 4 字节               |
| Adam 一阶矩 \(m\)           | 4 字节               |
| Adam 二阶矩 \(v\)           | 4 字节               |
| **合计**                    | **16 字节**          |

因此，70 亿参数的模型：

- FP16 权重本身约 **14 GB**。
- 上述训练状态合计约 **112 GB**。
- 还没计入激活值、通信缓冲等开销。

这是特定精度和优化器配置下的估算，不同实现的梯度精度、主参数策略可能不同。[ZeRO 论文的显存分析](https://arxiv.org/html/1910.02054v3)

普通 DDP 会在每张 GPU 上重复保存这些状态。ZeRO 从这种重复入手，分三个阶段逐步减少副本。

**2. 三个阶段的整体区别**

设完整参数、梯度、优化器状态分别占 \(P、G、O\)，分片组中有 \(N\) 张 GPU：

| 方案   | 参数 | 梯度 | 优化器状态 | 每卡理想常驻占用 |
| ------ | ---- | ---- | ---------- | ---------------- |
| DDP    | 完整 | 完整 | 完整       | \(P+G+O\)        |
| ZeRO-1 | 完整 | 完整 | 分片       | \(P+G+O/N\)      |
| ZeRO-2 | 完整 | 分片 | 分片       | \(P+(G+O)/N\)    |
| ZeRO-3 | 分片 | 分片 | 分片       | \((P+G+O)/N\)    |

阶段是累加的：ZeRO-3 包含前两个阶段的分片能力。

这里说的是**常驻状态**。计算过程中仍可能出现临时完整参数和梯度缓冲，因此它不等于实际峰值显存。[DeepSpeed 三阶段定义](https://www.deepspeed.ai/tutorials/zero/)

**3. ZeRO-1：把优化器状态分给不同 GPU**

假设模型参数划分为四组：

```
完整模型参数： [ P₀ | P₁ | P₂ | P₃ ]
```

在 DDP 中，每张 GPU 都维护四组参数对应的 Adam 状态；在 ZeRO-1 中：

```
GPU 0：完整参数 + 完整梯度 + P₀ 对应的优化器状态
GPU 1：完整参数 + 完整梯度 + P₁ 对应的优化器状态
GPU 2：完整参数 + 完整梯度 + P₂ 对应的优化器状态
GPU 3：完整参数 + 完整梯度 + P₃ 对应的优化器状态
```

这样做为什么可行？

因为 Adam 对某个参数进行更新时，主要需要该参数自己的梯度、历史一阶矩和二阶矩。**没有必要让四张卡重复执行并保存同一份参数更新。**

可以把一次迭代理解为：

```
各卡用不同数据执行前向、反向
              ↓
聚合梯度
              ↓
每张卡更新自己负责的参数分片
              ↓
交换更新后的参数，恢复每卡完整参数
```

例如 GPU 0 负责更新 \(P_0\)，GPU 1 负责更新 \(P_1\)。最后把各自更新好的部分交换出去，所有卡又有了相同的完整参数。

这是理解流程的逻辑模型；具体实现可以调整梯度归约和参数交换的方式。[DeepSpeed ZeRO 说明](https://www.deepspeed.ai/tutorials/zero/)

**4. ZeRO-2：更新哪个参数，就保留哪个参数的聚合梯度**

ZeRO-1 中，每张 GPU 仍保存完整梯度。

但 GPU 0 只更新 \(P_0\)，它真正需要长期保留的，只是 \(P_0\) 对应的聚合梯度。ZeRO-2 因此进一步分片梯度：

```
GPU 0：完整参数 + G₀ + 优化器状态 O₀
GPU 1：完整参数 + G₁ + 优化器状态 O₁
GPU 2：完整参数 + G₂ + 优化器状态 O₂
GPU 3：完整参数 + G₃ + 优化器状态 O₃
```

这里最重要的一点是：

**\(G_0\) 是所有卡的数据共同贡献、聚合后得到的第 0 份梯度；它不是 GPU 0 自己那批数据的梯度。**

用两张 GPU、两个参数举例：

```
GPU 0 本地算出的梯度：[2,  6]
GPU 1 本地算出的梯度：[4, 10]

全局平均梯度：      [3,  8]
```

DDP 会让两张卡都获得 `[3, 8]`。

ZeRO-2 则可以通过 **ReduceScatter，并配合平均所需的缩放**，得到：

```
GPU 0：只保留第一个参数的平均梯度 3
GPU 1：只保留第二个参数的平均梯度 8
```

随后：

```
GPU 0 更新第一个参数
GPU 1 更新第二个参数
          ↓
AllGather 更新后的参数
          ↓
两张 GPU 都拥有完整的新参数
```

所以 ZeRO-2 的典型通信结构是：

```
梯度：ReduceScatter
参数：更新后 AllGather
```

各卡仍然计算自己数据对整个模型的梯度贡献，只是梯度可以按桶归约、分片、释放，避免长期保留完整梯度。[DeepSpeed 梯度归约与参数收集配置](https://deepspeed.readthedocs.io/en/latest/zero3.html)

**5. ZeRO-3：参数也分片，计算前再临时收集**

ZeRO-2 中，模型参数仍然每卡完整保存。如果权重本身就很大，这部分依然会限制模型规模。

ZeRO-3 把参数也分片：

```
GPU 0：P₀ + G₀ + O₀
GPU 1：P₁ + G₁ + O₁
GPU 2：P₂ + G₂ + O₂
GPU 3：P₃ + G₃ + O₃
```

**参数不完整，怎么做前向计算？**

答案是：**算到哪个模块，就临时收集哪个模块所需的参数。**

例如一个模型有三个模块：

```
输入 → 模块 A → 模块 B → 模块 C → loss
```

前向流程可以理解为：

```
AllGather A 的参数 → 计算 A → 释放临时完整参数
AllGather B 的参数 → 计算 B → 释放临时完整参数
AllGather C 的参数 → 计算 C → 释放临时完整参数
```

这里每张 GPU 使用收集到的模块参数，处理的是**自己那批样本**。

反向传播时，如果之前释放了完整参数，就需要再次收集：

```
收集 C 参数 → C 反向 → 梯度 ReduceScatter
收集 B 参数 → B 反向 → 梯度 ReduceScatter
收集 A 参数 → A 反向 → 梯度 ReduceScatter
```

最后，每张卡使用自己持有的梯度分片和优化器状态，更新自己的参数分片。下一次计算时，其他卡再按需获取这些新参数。

参数何时释放、是否保留小参数、是否预取下一模块，都可以影响显存和性能。这不是“每一步都收集整个模型”。[ZeRO-3 参数管理机制](https://deepspeed.readthedocs.io/en/latest/zero3.html)

**为什么反向传播还需要参数？**

以线性层为例：

\[ Y=XW \]

反向传播中，传给前一层的梯度包含：

\[ \frac{\partial L}{\partial X} =\frac{\partial L}{\partial Y}W^\top \]

因此，计算输入梯度时仍需要 \(W\)。如果前向后释放了它，就需要重新获取。

另外，参数分片可以切到张量内部，并不意味着“GPU 0 固定计算第一层、GPU 1 固定计算第二层”。

**6. 显存节省到底有多大？**

沿用前面 70 亿参数、经典 FP16 Adam 的假设，使用 **8 张 GPU**：

\[ P=14\text{ GB},\quad G=14\text{ GB},\quad O=84\text{ GB} \]

由前面的分片公式，可以得到：

| 方案   | 每卡理想常驻训练状态           |
| ------ | ------------------------------ |
| DDP    | 112 GB                         |
| ZeRO-1 | \(14+14+84/8=\) **38.5 GB**    |
| ZeRO-2 | \(14+(14+84)/8=\) **26.25 GB** |
| ZeRO-3 | \(112/8=\) **14 GB**           |

但不能据此认定 ZeRO-3 用 16 GB 显卡就一定能训练这个模型。实际还要容纳：

- 本卡数据产生的激活值。
- 当前计算模块临时收集的参数。
- 梯度与通信缓冲区。
- CUDA 工作空间和内存分配开销。

因此，**训练状态按 \(1/N\) 分片，不代表总显存也严格按 \(1/N\) 缩小。**

**7. 更省显存，会不会通信更多？**

需要分阶段看。

在经典分析中，AllReduce 可以理解成两个逻辑部分：

```
ReduceScatter → AllGather
```

DDP 用它们聚合并恢复完整梯度。ZeRO-2 则把通信安排为：

```
ReduceScatter 梯度 → 更新分片 → AllGather 参数
```

在张量大小、精度等假设一致的理想模型下，**ZeRO-2 可以保持与 DDP 相当的通信量**。

ZeRO-3 还要在前向和反向时收集参数。原论文的简化分析中，其通信量约为 DDP 的 **1.5 倍**；这不是所有实现和配置的固定性能比例。[原论文通信分析](https://arxiv.org/html/1910.02054v3#S7)

实际速度还取决于通信次数、参数预取、计算通信重叠，以及 GPU 互联带宽。也因此，NVLink、NVSwitch 和 InfiniBand 会影响 ZeRO 的执行效率。

**8. ZeRO 与其他技术怎么配合？**

| 技术                         | 主要解决什么问题               |
| ---------------------------- | ------------------------------ |
| **ZeRO**                     | 分片参数、梯度、优化器状态     |
| **Activation checkpointing** | 少存激活值，反向时重新计算     |
| **Offload**                  | 把部分状态放到 CPU 内存或 NVMe |
| **张量并行 TP**              | 把单个算子的计算拆到多张 GPU   |
| **流水线并行 PP**            | 把不同层的计算分配到不同 GPU   |

这些技术可以组合使用。

例如，ZeRO-3 降低训练状态占用，activation checkpointing 降低激活值占用；如果仍然放不下，可以进一步 offload。优化器 offload 还可以把更新计算交给 CPU，但会引入主机与 GPU 之间的数据搬运。[ZeRO-Offload 文档](https://www.deepspeed.ai/tutorials/zero-offload/)

PyTorch 的 **FSDP** 也采用参数按需收集、梯度归约分片的思路，完整分片模式与 ZeRO-3 属于相近的技术路线，但两者的 API、调度和实现并不相同。[PyTorch FSDP 文档](https://docs.pytorch.org/docs/stable/distributed.fsdp.fully_shard.html)



## **FSDP**

**PyTorch、DeepSpeed、ZeRO-3 与 FSDP 的关系**

| 名称          | 定位                                               | 主要作用                                                 |
| ------------- | -------------------------------------------------- | -------------------------------------------------------- |
| **PyTorch**   | 基础深度学习框架                                   | 提供张量计算、自动求导、模型定义、优化器及分布式训练能力 |
| **DeepSpeed** | 通常配合 PyTorch 使用的训练与推理优化库／运行时    | 提供 ZeRO、Offload、并行训练及性能优化                   |
| **ZeRO-3**    | ZeRO 的第三阶段算法，也常指 DeepSpeed 中的具体实现 | 分片参数、梯度和优化器状态，降低每卡显存占用             |
| **FSDP**      | PyTorch 原生的分片数据并行方案                     | 完整分片模式采用与 ZeRO-3 相近的机制                     |

```
PyTorch：模型、张量计算、自动求导
   │
   ├── 原生分布式方案：DDP / FSDP
   │
   └── 配合 DeepSpeed：ZeRO-1 / ZeRO-2 / ZeRO-3 等
```

**从 DDP 到完整分片**

普通 DDP 中，每张 GPU 保存完整模型、梯度和优化器状态，处理不同数据，通过 AllReduce 同步梯度。

ZeRO 逐步减少这些状态的重复副本：

| 方案   | 参数 | 梯度 | 优化器状态 |
| ------ | ---- | ---- | ---------- |
| DDP    | 完整 | 完整 | 完整       |
| ZeRO-1 | 完整 | 完整 | 分片       |
| ZeRO-2 | 完整 | 分片 | 分片       |
| ZeRO-3 | 分片 | 分片 | 分片       |

**ZeRO-3 与 FSDP 完整分片的共同流程**

```
平时：每卡保存训练状态的不同分片
                  ↓
计算模块前：AllGather 收集所需的完整参数
                  ↓
各卡用自己的数据执行计算
                  ↓
反向传播：ReduceScatter 聚合梯度并分片
                  ↓
各卡更新自己负责的参数分片
```

参数用完后可释放临时完整副本；反向计算需要时再收集。预取和保留策略会影响通信与显存占用。

**梯度分片包含所有卡的数据贡献，不是只使用分片所在 GPU 的样本。**

**FSDP2 与 DeepSpeed ZeRO-3 的主要区别**

| 维度     | FSDP2                                          | DeepSpeed ZeRO-3                             |
| -------- | ---------------------------------------------- | -------------------------------------------- |
| 接入方式 | 对模型应用 `fully_shard()`                     | 通过 `deepspeed.initialize()` 创建 engine    |
| 训练循环 | 通常使用 `loss.backward()`、`optimizer.step()` | 通常由 engine 管理反向传播和更新             |
| 参数表示 | 使用 DTensor 表示逐参数分片                    | 使用 DeepSpeed 的参数分片管理机制            |
| 调度控制 | 显式模块分组、重新分片与预取策略               | 通过引擎配置控制预取、参数保留和释放等       |
| 卸载     | 标准接口支持 CPU Offload                       | 支持 CPU，以及 ZeRO-Infinity 的 NVMe Offload |

**需要记住的边界**

- FSDP 完整分片与 ZeRO-3 思路相近，但不是同一份实现，也不能直接互换配置和训练检查点。
- 二者仍属于数据并行：各卡处理不同数据；张量并行则把一个算子的计算拆到多张卡。
- 理想情况下，完整分片使每卡常驻训练状态接近  \[ \frac{\text{参数}+\text{梯度}+\text{优化器状态}}{N} \]但实际峰值还包含激活值、临时完整参数和通信缓冲。
- 两者没有固定的速度或显存优势，需要在相同模型、精度、有效 batch 和硬件条件下比较。

### FSDP与FSDP2

这里的“FSDP”通常指旧版 **FSDP1**，其 API 是 `FullyShardedDataParallel`；**FSDP2 是重新设计的实现，核心 API 是 `fully_shard()`**。

**两者的训练原理相近，最大的变化是：FSDP1 按扁平参数组分片，FSDP2 按单个参数分片，并用 DTensor 表示。**

| 维度     | FSDP1                                      | FSDP2                                           |
| -------- | ------------------------------------------ | ----------------------------------------------- |
| 使用方式 | 用 `FSDP(...)` 包装模块                    | 对原模块调用 `fully_shard(...)`                 |
| 参数分片 | 一组参数展平、拼接后分片                   | 每个参数分别分片，默认沿第 0 维                 |
| 参数表示 | 底层使用 `FlatParameter`                   | 使用 DTensor                                    |
| 通信分组 | 由包装边界决定，可使用 `auto_wrap_policy`  | 由应用 `fully_shard()` 的模块边界显式决定       |
| 显存管理 | 可能通过 CPU 限流控制预取占用              | 重新设计多 stream 内存管理，使占用更可预测      |
| 冻结参数 | 同组混合冻结／非冻结参数存在限制或额外开销 | 支持更自然，无需由此增加梯度存储                |
| 检查点   | 提供多种 state dict 模式                   | 分片状态使用 DTensor，配合 DCP 等接口保存、恢复 |

这些是实现和接口的变化，并不意味着 FSDP2 在所有任务中都更快。[FSDP2 官方对比](https://docs.pytorch.org/docs/stable/distributed.fsdp.fully_shard.html)

**1. 最核心的区别：参数怎么切**

假设同一组中有两个参数：

```
W₁ = [a b]    W₂ = [e f]
     [c d]         [g h]
```

使用两张 GPU。

**FSDP1：先展平、拼接，再切分。**

```
拼接：[a b c d e f g h]

GPU 0：[a b c d]    ← 持有 W₁ 的数据
GPU 1：[e f g h]    ← 持有 W₂ 的数据
```

**FSDP2：每个参数沿第 0 维分别切分。**

```
GPU 0：W₁ 的第一行 [a b]，W₂ 的第一行 [e f]
GPU 1：W₁ 的第二行 [c d]，W₂ 的第二行 [g h]
```

这样每个分片仍能明确对应原始参数，便于检查参数、配置优化器和处理分布式状态。

注意：FSDP1 即使设置 `use_orig_params=True`，底层仍然依赖扁平参数，暴露的原始参数是其视图。[FSDP1 参数说明](https://docs.pytorch.org/docs/stable/fsdp.html)

**2. API 从“包装模型”变为“对模型应用能力”**

FSDP1 的典型写法：

```
from torch.distributed.fsdp import FullyShardedDataParallel as FSDP

model = FSDP(
    model,
    auto_wrap_policy=policy,
)
```

FSDP2 的典型写法：

```
from torch.distributed.fsdp import fully_shard

for block in model.blocks:
    fully_shard(block)

fully_shard(model)

# 分片之后创建优化器
optimizer = torch.optim.AdamW(model.parameters())
```

FSDP2 直接为原模块添加分片管理能力，并保留原模型的类型关系。每个被应用 `fully_shard()` 的模块，形成对应的参数通信组。[官方教程](https://docs.pytorch.org/tutorials/intermediate/FSDP_tutorial.html)

**3. 分片策略的配置方式也变了**

常见迁移关系是：

| FSDP1           | FSDP2                                                   |
| --------------- | ------------------------------------------------------- |
| `FULL_SHARD`    | `reshard_after_forward=True`                            |
| `SHARD_GRAD_OP` | `reshard_after_forward=False`                           |
| `HYBRID_SHARD`  | 二维 DeviceMesh，加前向后重新分片                       |
| `no_sync()`     | 使用 `set_requires_gradient_sync(False)` 等接口管理同步 |

其中，`reshard_after_forward` 决定前向后是否释放完整参数：

- `True`：更省显存，反向前需要重新收集。
- `False`：保留完整参数供反向使用，减少通信，但占用更多显存。

迁移时还需要检查模型初始化、精度策略和检查点接口，不能只替换类名。[官方迁移指南](https://docs.pytorch.org/tutorials/intermediate/FSDP_tutorial.html#fsdp1-to-fsdp2-migration-guide)

**4. 算法层面没有变成另一种并行方式**

在完整分片配置下，两者仍然采用：

```
参数分片保存
    ↓ AllGather
恢复当前模块参数，执行计算
    ↓ ReduceScatter
聚合并分片梯度
    ↓
各卡更新自己的参数分片
```

**FSDP2 的主要进步在参数表示、内存管理和接口可组合性；它仍然是全分片数据并行。** 当前官方教程已将 FSDP1 标为弃用，新代码通常优先考虑 FSDP2。

## 零气泡流水线

**1. 零气泡的关键：把反向传播拆成两部分**

普通调度往往把一次反向看成一个整体。但对当前阶段来说，反向至少包含两类任务：

| 任务                         | 计算什么                       | 谁需要它                           |
| ---------------------------- | ------------------------------ | ---------------------------------- |
| **输入梯度计算，记作 \(B\)** | \(\partial L/\partial X\)      | 前一个流水线阶段，用来继续反向传播 |
| **参数梯度计算，记作 \(W\)** | \(\partial L/\partial \theta\) | 当前阶段，用来更新参数             |

这里 \(W\) 表示**计算参数梯度**，还不是执行优化器更新。

以线性层为例：

\[ Y=X\theta \]

给定输出梯度 \(G_Y=\partial L/\partial Y\)，需要计算：

\[ G_X=G_Y\theta^\top \]\[ G_\theta=X^\top G_Y \]

这两项的紧急程度不同：

- **\(G_X\) 很紧急**：前一个阶段正等着它继续反向。
- **\(G_\theta\) 可以稍后计算**：只要在该次参数更新需要它之前完成即可。

因此，零气泡调度会优先计算并发送输入梯度，把部分参数梯度计算推迟到原本空闲的时段。[Zero Bubble 原论文](https://arxiv.org/html/2401.10241v1)

**2. 它怎样用参数梯度计算填补空闲？**

传统调度可以理解为：

```
当前阶段：
[计算输入梯度 + 参数梯度] → 向前一阶段发送输入梯度
```

细分后可以安排为：

```
当前阶段：
[计算输入梯度] → 立即发送
                      ↓
          参数梯度计算留待合适时机执行
```

前一阶段因此更早开始工作。与此同时，当前阶段以后遇到依赖等待时，可以执行已经具备输入条件的参数梯度任务。

局部效果类似：

```
普通调度： [有效计算][等待数据][有效计算]
改进调度： [有效计算][参数梯度计算][有效计算]
```

**计算没有被省略，只是重新排列了执行时间。** 在保持同步训练语义的同时，这种更细的调度可以显著降低气泡。

## 张量并行

**张量并行（TP）**：把同一个层的参数和计算拆到多张 GPU，各卡处理同一批样本，共同完成这一层的运算。

| 切分方式，以 \(Y=XW\) 为例        | 各卡计算什么         | 如何组合           |
| --------------------------------- | -------------------- | ------------------ |
| 按 \(W\) 的列切分                 | 输出的不同特征分片   | 需要完整输出时拼接 |
| 按 \(W\) 的行切分，同时切分 \(X\) | 同一输出的不同部分和 | 求和               |

**反向传播需要区分两类梯度：**

- **参数梯度**：用于更新当前层的参数。
- **输入梯度**：交给前一层，继续计算导数。“向前一层传播”不一定跨 GPU；跨卡传输或归约才是通信。

**为什么需要合并梯度？**

同一个输入或共享参数可能影响多个分支，其完整梯度等于各分支贡献之和：

\[ G=g_0+g_1 \]

这是链式法则中的**求和**，不是 DDP 对不同数据梯度的平均。

**可以一直分开反向吗？**

可以。各分支可以独立反向到结束，再合并**每个共享参数**的梯度贡献，不要求每层立即合并。但必须基于同一次前向的参数和激活值。

**哪些必须合并，哪些不用？**

- 不同分支对**同一个参数**的贡献：更新时必须全部考虑。
- 各卡负责的**不同参数**的梯度：无需互相相加。
- 合并后不必每卡都保存完整梯度；可以通过 ReduceScatter，让各卡只获得自己负责更新的参数梯度。

## 序列并行

**序列并行（Sequence Parallelism，SP）是沿序列中的 token 位置切分激活值，让不同 GPU 负责不同位置的部分计算，从而减少激活值显存和重复计算。**

结合前面的 TP，下面先讲与张量并行配合的经典 SP。[PyTorch 官方介绍](https://docs.pytorch.org/tutorials/intermediate/TP_tutorial.html)

**1. 到底切分什么？**

Transformer 中，激活值通常是：

\[ X\in\mathbb{R}^{B\times S\times H} \]

其中：

- \(B\)：batch 中的样本数。
- \(S\)：每个样本的序列长度。
- \(H\)：每个 token 的隐藏特征维度。

假设只有一个样本、8 个 token，使用两张 GPU：

```
完整序列：t₀ t₁ t₂ t₃ t₄ t₅ t₆ t₇

GPU 0：  t₀ t₁ t₂ t₃
GPU 1：              t₄ t₅ t₆ t₇
```

**每张卡保存部分 token 的完整隐藏向量。** 例如原激活值是 `[1, 8, 4096]`，每卡对应的序列分片就是 `[1, 4, 4096]`。

这与数据并行不同：数据并行通常分配不同样本，SP 分配的是**同一样本中的不同 token 位置**。

**2. 为什么可以分开计算？**

因为有些操作不需要不同 token 之间交换信息。

例如，常见的 LayerNorm、RMSNorm 是对**每个 token 自己的隐藏向量**做归一化：

```
token 0 的归一化，只需要 token 0 的特征
token 1 的归一化，只需要 token 1 的特征
……
```

因此可以：

```
GPU 0：对 token 0～3 执行归一化
GPU 1：对 token 4～7 执行归一化
```

各卡无需为了归一化而收集整个序列。经典 SP 主要利用这类逐 token 操作，包括归一化，以及相应的逐元素操作。[PyTorch SequenceParallel 接口](https://docs.pytorch.org/docs/stable/distributed.tensor.parallel.html)

**3. 它怎样与张量并行配合？**

普通 TP 会切分 Attention、MLP 中的参数和计算，但在一些模块边界，各卡仍可能保存相同的完整激活值。

SP 让这些边界上的激活值保持序列分片。典型流程是：

```
序列分片的激活值
        ↓
各卡处理自己 token 的 LayerNorm / RMSNorm
        ↓ AllGather
恢复完整序列的输入
        ↓
Attention 或 MLP 内部使用 TP，分片计算
        ↓ ReduceScatter
归约部分结果，并按 token 位置分给各卡
        ↓
序列分片的激活值，进入后续计算
```

因此：

- **TP** 主要拆分层内部的参数与计算，例如隐藏特征或 attention heads。
- **SP** 让部分激活值及相关计算沿 token 位置分布。

二者经常使用同一组 GPU 配合执行。[PyTorch TP＋SP 示例](https://docs.pytorch.org/tutorials/intermediate/TP_tutorial.html#apply-sequence-parallel-to-layernorm-rmsnorm-layers)

**4. Attention 能直接各算各的 token 吗？**

**不能把两个序列片段当成互不相关的句子，各自独立做完整 Attention。**

因为一个 token 可能需要关注其他 GPU 上的 token。例如，因果注意力中，后半段 token 通常需要访问前半段 token 的 Key、Value。

所以：

```
逐 token 的归一化：可以直接在序列分片上独立计算
跨 token 的 Attention：需要相应通信或布局转换
```

经典 TP＋SP 通常在进入 Attention 前收集输入序列，再按 head 等维度执行 TP。

另一类 **上下文并行（Context Parallelism，CP）** 会把序列切分进一步用于 Attention，通过交换 KV 等方式完成跨片段注意力，更直接地面向长上下文训练。有些资料也把这类方案称作“序列并行”，阅读时需要确认具体定义。[PyTorch Context Parallel 介绍](https://docs.pytorch.org/tutorials/unstable/context_parallel.html)

**5. 反向传播还需要通信吗？**

需要。激活值布局的转换，在反向中也有对应的梯度通信。

此外，即使各卡处理不同 token，如果使用的是同一组归一化参数，这些参数的梯度也要汇总各 token 的贡献，才能正确更新。

SP 节省的是**部分激活值及相关计算的重复开销**，不意味着整个模型显存都会严格降到原来的 \(1/N\)。

## 专家并行

**专家并行（Expert Parallelism，EP）是把同一个 MoE 层中的不同专家分配到不同 GPU 上，再根据路由结果，把 token 发送给对应专家计算。**

**1. 专家怎样放到不同 GPU？**

假设一个 MoE 层有 4 个专家，使用两张 GPU：

```
GPU 0：专家 E₀、E₁
GPU 1：专家 E₂、E₃
```

在这个基本配置中，每张卡保存自己负责专家的完整参数及相关训练状态，不需要保存其他专家的完整副本。

如果单个专家也很大，还可以结合 TP，将一个专家内部的矩阵计算继续拆分。[DeepSpeed 专家并行配置](https://www.deepspeed.ai/tutorials/mixture-of-experts/)

**2. 前向传播：token 去找专家**

假设两张卡最初各有一个 token，使用 Top-2 路由：

```
GPU 0 的 token A → 专家 E₀、E₂
GPU 1 的 token B → 专家 E₁、E₂
```

执行过程如下。

**第一步：路由。**

Router 根据 token 的隐藏向量，计算目标专家和对应权重。

**第二步：分发（Dispatch）。**

```
token A：
  发给 GPU 0 的 E₀，本地处理
  发给 GPU 1 的 E₂，跨卡发送

token B：
  发给 GPU 0 的 E₁，跨卡发送
  发给 GPU 1 的 E₂，本地处理
```

传输的主要是 token 的隐藏向量及必要的路由信息，而不是把专家权重搬到 token 所在的卡。

**第三步：专家计算。**

```
GPU 0：
  E₀ 处理 A
  E₁ 处理 B

GPU 1：
  E₂ 批量处理 A、B
  E₃ 本次没有任务
```

实际实现会把发往同一专家的 token 组织成批次，进行矩阵计算。

**第四步：返回并合并（Combine）。**

专家输出返回原来负责该 token 的位置，然后按路由权重组合：

\[ y_A=\alpha_0E_0(x_A)+\alpha_2E_2(x_A) \]\[ y_B=\beta_1E_1(x_B)+\beta_2E_2(x_B) \]

结果恢复为原本的 token 顺序，进入后续网络。

多卡分发和回收常使用 **All-to-All** 或专门优化的通信实现。**All-to-All 不意味着每个 token 都发给全部 GPU；token 只需要送往选中专家所在的位置。** [DeepSeek-V3 通信实现](https://arxiv.org/html/2412.19437v2)

**3. 反向传播怎么做？**

反向沿前向的数据路径返回：

```
token 原位置获得输出梯度
            ↓
根据路由权重，把梯度发给选中的专家
            ↓
各专家计算：
  ① 自己的参数梯度
  ② 对 token 输入的梯度贡献
            ↓
输入梯度贡献返回 token 原位置
            ↓
合并贡献，继续向前面的网络反向传播
```

同一个 token 经过多个专家，其输入梯度需要汇总各专家路径的贡献；完整反向还需要计入 Router 对该 token 的依赖所产生的梯度。

不同专家拥有不同参数，因此 **不能把 E₀ 的参数梯度与 E₂ 的参数梯度相加**。每个专家使用分配给自己的 token 贡献的梯度更新参数。

如果同一个专家还有数据并行副本，则需要在这些副本之间同步梯度。

**4. EP 与 TP、PP 有什么区别？**

| 方式     | 拆分什么                     | token 如何参与计算          |
| -------- | ---------------------------- | --------------------------- |
| **EP**   | 同一 MoE 层的不同专家        | 路由到少数被选中的专家      |
| **TP**   | 一个层或专家内部的矩阵计算   | 多张 GPU 合作完成同一个算子 |
| **PP**   | 模型的不同层                 | token 依次经过多个阶段      |
| **FSDP** | 参数、梯度、优化器状态的存储 | 按需收集当前模块参数后计算  |

EP 的特点是：**计算任务分配随 token 的路由结果动态变化**，不是固定让所有 token 经过全部专家。

**5. EP 的主要收益和瓶颈**

**收益是专家存储可以分散。** 增加专家数量时，可以用更多 GPU 容纳参数，而每个 token 仍只激活少数专家。

但运行效率主要受三个因素影响：

- **负载不均衡**：热门专家忙，其他专家空闲，整批计算可能被最忙的专家拖慢。
- **通信开销**：token 分发和结果返回需要搬运激活值，跨节点时成本尤其明显。
- **专家批次过小**：每个专家只收到少量 token 时，矩阵计算可能难以充分利用 GPU。

因此，实际系统通常结合负载均衡路由、专家放置、批量计算，以及通信计算重叠来提高效率。[DeepSeek-V3 的专家并行与调度设计](https://arxiv.org/html/2412.19437v2)

## 上下文并行

**上下文并行（Context Parallelism，CP）把同一条长序列沿 token 位置分给多张 GPU，并通过通信，让每个 token 仍能访问 Attention 所需的完整上下文。**

它主要解决：**序列太长，单张 GPU 放不下激活值，或无法高效完成计算。** [Megatron Core 官方介绍](https://docs.nvidia.com/megatron-core/developer-guide/latest/user-guide/features/context_parallel.html)

**1. 它怎样切分序列？**

假设一个样本有 8 个 token，使用两张 GPU：

```
完整序列：t₀ t₁ t₂ t₃ t₄ t₅ t₆ t₇

GPU 0：  t₀ t₁ t₂ t₃
GPU 1：              t₄ t₅ t₆ t₇
```

各卡主要保存自己 token 对应的激活值，执行这些位置的计算。

**它们仍然是同一个训练样本**，保持原来的全局位置和注意力掩码，不是两条独立的短句子。

单独使用 CP 时，模型参数通常在 CP 组内复制；CP 主要切分序列及激活值，参数存储还可以通过 TP、FSDP 等方式进一步分担。

**2. 普通层容易拆，Attention 为什么麻烦？**

对于逐 token 的 Linear、MLP、LayerNorm：

```
GPU 0 处理自己的 token
GPU 1 处理自己的 token
```

这些操作不需要其他位置的 token，可以在本地完成。

但 Attention 需要跨 token 交互：

\[ O=\operatorname{softmax} \left(\frac{QK^\top}{\sqrt d}+M\right)V \]

其中 \(M\) 是注意力掩码。

分片后，两张卡分别拥有：

```
GPU 0：Q₀、K₀、V₀
GPU 1：Q₁、K₁、V₁
```

GPU 0 要计算自己 token 的输出，除了本地 \(K_0、V_0\)，还可能需要 GPU 1 的 \(K_1、V_1\)：

\[ O_0= \operatorname{softmax} \left( \frac{Q_0[K_0;K_1]^\top}{\sqrt d}+M_0 \right) [V_0;V_1] \]

**Q 对应本卡负责的 token，KV 则需要覆盖这些 token 允许关注的位置。** 因果 Attention 会按掩码排除未来位置。[Megatron CP 的 Attention 通信](https://docs.nvidia.com/megatron-core/developer-guide/latest/user-guide/features/context_parallel.html)

**3. 怎样获得其他卡的 KV？**

一种直接方法是 AllGather：先收集 KV，再执行本地 Q 对完整 KV 的 Attention。但这会增加临时存储。

另一种常见方法是 **Ring Attention**：让 KV 分块在 GPU 之间轮转。

例如 4 张 GPU：

```
GPU 0 → GPU 1 → GPU 2 → GPU 3 → GPU 0
```

每张卡：

1. 保留自己的 Q。
2. 对当前 KV 块计算一部分 Attention。
3. 将 KV 块传给下一张卡，同时接收另一个块。
4. 继续计算，直到覆盖所有需要的 KV。

这样可以分块访问上下文，不必始终保存完整序列的 KV，并有机会重叠通信和计算。[Ring Attention 论文](https://arxiv.org/abs/2310.01889)

**这里不能对每个 KV 块单独做 softmax，再直接相加。** 各块必须共同满足全局 softmax 的归一化，通常用在线归一化方法合并结果。

**4. 反向传播怎么做？**

每张卡负责自己输出 token 的反向计算，但远端 KV 也参与了这些输出，因此需要把梯度贡献送回去。

例如：

```
GPU 0 的输出使用了 GPU 1 的 K₁、V₁
                    ↓
反向时算出对 K₁、V₁ 的梯度贡献
                    ↓
发送给 GPU 1，与其他贡献合并
```

因此：

- 本地 Q 的梯度由对应输出计算得到。
- 同一 KV 被多个 Q 分片使用，其梯度需要归约。
- CP 组内共享的模型参数，也需要按全局 loss 定义聚合各序列分片的参数梯度。

这些通信可以通过环形点对点传输等方式组织。[Megatron CP 前向与反向机制](https://docs.nvidia.com/megatron-core/developer-guide/latest/user-guide/features/context_parallel.html)

**5. CP 与前面讲的 SP 有什么不同？**

这里的 SP 指经典的 **Megatron 式、与 TP 配合的序列并行**：

| 对比               | 经典 SP                                 | CP                                             |
| ------------------ | --------------------------------------- | ---------------------------------------------- |
| 切分维度           | 序列维度                                | 序列维度                                       |
| 主要作用范围       | LayerNorm、Dropout 等区域的激活值与计算 | 序列输入及更广泛的激活值，包括分布式 Attention |
| Attention 如何处理 | 通常先转换布局，交给 TP 计算            | 跨序列分片交换 KV 等信息                       |
| 主要目标           | 减少 TP 中重复的激活值存储与计算        | 承载更长上下文、分担长序列计算                 |
| 并行组             | 通常使用已有 TP 组                      | 可以作为独立维度，与 TP 等组合                 |

不同资料可能把 CP 或其他长序列方案也称为“序列并行”，所以应看具体实现，而不能只看名字。[PyTorch CP 介绍](https://docs.pytorch.org/tutorials/unstable/context_parallel.html)

**6. 收益和代价**

CP 可以降低每卡的序列激活值占用，并分担长序列计算。但：

- 需要额外的 Attention 通信。
- 因果 Attention 中，越靠后的 token 可关注的位置越多，可能需要重新安排 token 分片来均衡负载。
- 参数、临时缓冲等开销不会全部按 CP 卡数缩小。
- 对普通完整 Attention，全局计算量仍随序列长度大致按平方增长；CP 是把工作分摊到多卡。

## 总结

**一、所有并行方式对比**

| 方式                      | 切分／优化对象               | 每张 GPU 主要负责什么                      | 主要通信                                   | 主要收益与代价                                  |
| ------------------------- | ---------------------------- | ------------------------------------------ | ------------------------------------------ | ----------------------------------------------- |
| **数据并行 DP／DDP**      | 不同样本                     | 保存完整模型，处理不同数据                 | AllReduce 聚合参数梯度                     | 提高吞吐；通常不降低单卡模型状态显存            |
| **ZeRO-1**                | 优化器状态                   | 完整参数、梯度；部分优化器状态             | 梯度归约、更新后交换参数                   | 减少优化器状态的重复存储                        |
| **ZeRO-2**                | 梯度＋优化器状态             | 完整参数；部分梯度与优化器状态             | 梯度 ReduceScatter、参数 AllGather 等      | 进一步省显存，参数仍每卡完整保存                |
| **ZeRO-3／FSDP 完整分片** | 参数＋梯度＋优化器状态       | 常驻保存状态分片，计算模块前收集参数       | 参数 AllGather、梯度 ReduceScatter         | 显著省模型状态显存；增加参数收集与调度开销      |
| **张量并行 TP**           | 一个层／算子内部的参数和计算 | 使用参数分片，共同完成同一个算子           | AllReduce、AllGather、ReduceScatter 等     | 分担大层的存储和计算；层间通信频繁              |
| **流水线并行 PP**         | 模型的不同层                 | 计算一个或多个模型阶段                     | 相邻阶段传递激活值和输入梯度               | 分担模型深度；存在流水线气泡                    |
| **零气泡流水线**          | PP 的执行顺序                | 将反向拆为输入梯度、参数梯度任务，重新调度 | 主要沿用 PP 通信                           | 减少空闲；受任务耗时、显存和同步条件限制        |
| **经典序列并行 SP**       | 部分激活值的 token 维度      | 在归一化等区域处理部分 token，通常配合 TP  | 激活值及梯度的 AllGather／ReduceScatter 等 | 减少 TP 中重复的激活值和计算                    |
| **上下文并行 CP**         | 同一长序列的 token 维度      | 处理部分 token，包括分布式 Attention       | KV 交换、KV 梯度归约、参数梯度聚合         | 降低长序列激活值占用；需要跨片段 Attention 通信 |
| **专家并行 EP**           | MoE 层的不同专家             | 保存部分专家，处理路由给它们的 token       | All-to-All 或优化的分发／回收通信          | 分散专家存储与计算；有负载不均和通信开销        |

其中，**DP 是并行策略，DDP 是其常见实现；ZeRO-3 与 FSDP 完整分片机制相近，但实现不同。** FSDP1、FSDP2 是实现版本，不是额外的并行维度。上表中的 SP 特指与 TP 配合的经典序列并行。[Megatron 并行指南](https://docs.nvidia.com/megatron-core/developer-guide/latest/user-guide/parallelism-guide.html)、[DeepSpeed ZeRO](https://deepspeed.readthedocs.io/en/latest/zero3.html)、[PyTorch TP／SP 教程](https://docs.pytorch.org/tutorials/intermediate/TP_tutorial.html)

**二、常见组合方式**

| 组合                         | 各部分怎样分工                                              | 适用目标                       |
| ---------------------------- | ----------------------------------------------------------- | ------------------------------ |
| **DP＋TP**                   | TP 组内合作计算模型；不同 DP 组处理不同样本                 | 同时扩大模型计算规模和数据吞吐 |
| **DP＋PP**                   | PP 组内按层接力；不同流水线副本处理不同数据                 | 深层模型训练                   |
| **DP＋TP＋PP**               | 数据、层内计算、模型深度三个方向共同拆分                    | 常说的“3D 并行”                |
| **FSDP／ZeRO＋TP**           | TP 拆算子；分片数据并行进一步分担对应参数、梯度、优化器状态 | 大模型的计算与显存扩展         |
| **TP＋SP**                   | TP 拆 Attention／MLP；SP 分担模块边界处的序列激活值         | 降低 TP 的激活值显存           |
| **TP＋CP**                   | TP 拆特征／head 等计算；CP 拆 token 位置                    | 大模型＋长上下文               |
| **PP＋零气泡调度**           | PP 决定层放在哪里；零气泡策略决定任务何时执行               | 降低流水线等待                 |
| **EP＋TP**                   | EP 分配不同专家；TP 继续拆分单个专家内部计算                | 单个专家也很大的 MoE           |
| **EP＋PP＋数据／状态分片**   | 按层分阶段、按专家分设备，再管理专家副本及训练状态          | 大规模 MoE                     |
| **TP＋PP＋CP＋分片数据并行** | 同时处理大层、深模型、长序列和训练状态显存                  | 大规模长上下文训练             |

## 屋顶线原理

**屋顶线模型（Roofline Model）用来判断一个程序的性能上限：它主要受限于“计算速度”，还是“数据搬运速度”。**

它回答的是“最多能跑多快、应该优化哪里”，不是“显存能否放下模型”。[NVIDIA Roofline 介绍](https://developer.nvidia.com/blog/accelerating-hpc-applications-with-nsight-compute-roofline-analysis/)

**1. 核心公式**

\[ \boxed{ P_{\text{实际}} \le \min\left(P_{\text{峰值}},\;B\times I\right) } \]

三个量分别是：

| 符号                | 含义                                           | 单位      |
| ------------------- | ---------------------------------------------- | --------- |
| \(P_{\text{峰值}}\) | 硬件在相应精度和计算类型下的峰值算力           | FLOP/s    |
| \(B\)               | 数据搬运带宽，例如 HBM 带宽                    | Byte/s    |
| \(I\)               | **算术强度**：每搬运一个字节，完成多少浮点运算 | FLOP/Byte |

其中：

\[ I=\frac{\text{浮点运算次数}}{\text{实际搬运的字节数}} \]

搬运量包含读取、写入，而不只是模型权重大小。讨论 HBM 屋顶线时，就应计算经过 HBM 的流量。[Nsight Compute 文档](https://docs.nvidia.com/nsight-compute/ProfilingGuide/)

**2. 为什么有两条性能上限？**

假设硬件：

```
计算单元：每秒最多计算 100 万亿次
显存带宽：每秒最多搬运 2 万亿字节
```

如果程序每搬运 1 字节，只做 10 次运算，那么显存每秒最多供应：

\[ 2\times10=20\text{ TFLOP/s} \]

所需的数据。

即使计算单元能达到 100 TFLOP/s，数据供不上，程序也无法达到这个速度。

反过来，如果每个字节能支持很多计算，数据供应足够，计算单元本身就成为上限。

**3. 为什么叫“屋顶线”？**

把算术强度画在横轴、计算性能画在纵轴，会出现一个先上升、再变平的边界：

```
计算性能
   ↑
   │               ───────────── 计算峰值
   │              /
   │             /
   │            /  带宽决定的上限
   │           /
   └──────────────────────────→ 算术强度
        带宽受限区       计算受限区
```

- **左边斜线**：\(P=B\times I\)。增加数据复用，提高算术强度，性能上限随之提高。
- **右边水平线**：\(P=P_{\text{峰值}}\)。计算能力已经成为上限。

程序的实测性能点通常位于这条“屋顶线”下面。

**4. 一个数值例子**

假设某种精度下：

\[ P_{\text{峰值}}=100\text{ TFLOP/s}, \qquad B=2\text{ TB/s} \]

则：

| 算术强度 \(I\) | 带宽允许的计算速度 \(BI\) | 两项约束下的性能上限  |
| -------------- | ------------------------- | --------------------- |
| 10 FLOP/Byte   | 20 TFLOP/s                | **20：带宽受限**      |
| 50 FLOP/Byte   | 100 TFLOP/s               | **100：两条上限交汇** |
| 100 FLOP/Byte  | 200 TFLOP/s               | **100：计算受限**     |

拐点为：

\[ I_{\text{拐点}}=\frac{P_{\text{峰值}}}{B}=50\text{ FLOP/Byte} \]

**硬件算力越强、带宽相对越小，就越需要高算术强度，才能充分利用计算单元。**

**5. 如何据此优化？**

| 瓶颈               | 优化方向                                                     |
| ------------------ | ------------------------------------------------------------ |
| **接近带宽屋顶**   | 减少数据搬运：分块复用、缓存复用、融合算子、减少中间结果读写 |
| **接近计算屋顶**   | 改善计算实现，或在允许时减少运算量、使用更合适的精度和计算单元 |
| **远低于两条屋顶** | 排查并行度不足、启动开销、访存低效、同步等待等问题           |

**增加算力，对一个已经受带宽限制的程序，可能几乎没有帮助。**

另外，HBM、L2、L1 可以分别建立带宽上限，形成分层 Roofline；分析时必须让算术强度与对应的存储层次匹配。[NERSC Roofline 文档](https://nersc.gitlab.io/tools/performance/roofline/)

**6. 与前面讨论的 TP、CP 有什么关系？**

分布式训练还可以加入“网络搬运”这一项。一个理想化的时间下界是：

\[ T\ge \max\left( \frac{\text{运算量}}{\text{计算能力}}, \frac{\text{HBM 流量}}{\text{HBM 带宽}}, \frac{\text{跨卡数据量}}{\text{网络带宽}} \right) \]

这假设计算与搬运可以充分重叠，实际还会受到通信延迟和同步等影响。

因此：

- **TP**：切分后，本卡计算变少，但跨卡通信可能成为瓶颈。
- **CP／Ring Attention**：块计算时间足够长，才有机会覆盖 KV 传输时间。
- **GPU／TPU**：不能只比较峰值算力，还要看带宽、数据复用和通信条件。

Roofline 给出的是性能上限；实测能否接近它，还取决于具体内核和执行效率。

## 论文报告中的配置

| 报告中的配置             | 含义                                                 |
| ------------------------ | ---------------------------------------------------- |
| **TP=8／8 路张量并行**   | 8 张卡共同完成被拆分的层内计算                       |
| **PP=4／4 路流水线并行** | 模型分成 4 个流水线阶段，由 4 个流水线 rank 接力计算 |
| **DP=16／16 路数据并行** | 16 个模型副本或数据并行成员处理不同样本，再聚合梯度  |
| **CP=2／2 路上下文并行** | 同一条序列分给 2 个成员，协作完成完整上下文计算      |
| **EP=8／8 路专家并行**   | 一个专家并行组包含 8 个成员，专家分布在这些成员上    |
| **FSDP 分片度=8**        | 训练状态在 8 个成员之间分片                          |
| **启用 SP**              | 经典 SP 通常复用 TP 组，一般不额外增加 GPU 倍数      |

“成员”指某个并行通信组中的进程，也就是 rank。在最常见的“一进程控制一张 GPU”配置下，可以直接理解为一张 GPU

**1. 多种并行度一起报告，怎样理解？**

假设论文写：

```
TP=4，PP=2，CP=2，DP=4
```

如果这些维度彼此独立，则：

\[ \text{总 GPU 数}=4\times2\times2\times4=64 \]

可以分层理解：

```
4 张卡做 TP
    ×
2 个流水线阶段
    ×
2 个上下文分片
    =
16 张卡共同处理一组完整序列的模型计算

再复制为 4 个数据并行组
    =
64 张卡
```

因此，**TP=4 不代表整个训练只用了 4 张卡，而是每个 TP 组有 4 张卡**；整个系统可以同时存在很多 TP 组。

**2. EP 路数不等于专家数量**

例如：

```
专家总数：64
EP=8
Top-K=2
```

三者分别表示：

- **64 个专家**：模型这一层有多少专家网络。
- **EP=8**：专家分布在 8 个成员上；简单均匀配置下，每卡放 8 个专家。
- **Top-K=2**：每个 token 选择 2 个专家计算。

EP 有时会复用或重组数据并行侧的设备，因此计算总卡数时，不能不看框架定义就再乘一个 EP。

**3. 并行路数不直接等于 batch size**

常见配置下：

\[ \text{全局 batch} = \text{每个数据副本的 micro-batch} \times \text{梯度累积次数} \times \text{DP 并行度} \]

例如 micro-batch 为 2、累积 8 次、DP=4：

\[ \text{全局 batch}=2\times8\times4=64 \]

**TP、PP、CP 是协作处理这些样本，不应再作为样本数量的倍数。**
