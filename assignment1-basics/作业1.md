## Problem（unicode2）

**（a）：** 为什么训练分词器时，我们更倾向于使用 UTF-8 编码的字节，而不是 UTF-16 或 UTF-32？

**ASCII 文本更紧凑：** 英文字母、数字、标点通常只需 1 字节，而 UTF-16 和 UTF-32 分别需要 2 和 4 字节，从而减少训练时需要处理的原始字节数量。

**减少重复的填充字节：** 对 ASCII 字符，UTF-16 和 UTF-32 会产生大量 `00` 字节，字节级 BPE 需要通过额外的合并来重新构建这些字符。

**没有大小端差异：** UTF-8 的字节顺序唯一，数据处理更简单；UTF-16 和 UTF-32 则需要明确使用大端序还是小端序。

**与常见文本数据格式一致：** 使用 UTF-8 可以减少数据转换的需要。

**（b）：** 下面这个函数试图将 UTF-8 字节串解码为 Unicode 字符串，但实现有误；请给出一个会产生错误结果的输入字节串，并用一句话解释原因。

```
def decode_utf8_bytes_to_str_wrong(bytestring: bytes):
    return "".join([bytes([b]).decode("utf-8") for b in bytestring])
```

**回答：** 例如输入 `b"\xc3\xa9"`（字符 `é` 的 UTF-8 编码）会触发 `UnicodeDecodeError`，因为 UTF-8 字符可能由多个字节组成，而该函数错误地将每个字节单独解码。

**（c）：** 给出一个无法按 UTF-8 解码为任何 Unicode 字符的双字节序列，并用一句话解释原因。

**回答：** 例如 `b"\x80\x80"` 无法按 UTF-8 解码，因为这两个字节都是续字节（以二进制 `10` 开头），而合法的 UTF-8 字节序列不能以续字节开头。

UTF-8 通过字节开头的几位，判断它在字符编码中的作用：

| 字节的二进制形式 | 含义                                         |
| ---------------- | -------------------------------------------- |
| `0xxxxxxx`       | 一个单字节字符                               |
| `110xxxxx`       | 双字节字符的第一个字节                       |
| `1110xxxx`       | 三字节字符的第一个字节                       |
| `11110xxx`       | 四字节字符的第一个字节                       |
| `10xxxxxx`       | 续字节，必须跟在某个多字节字符的起始字节后面 |

## 预分词

```python
PAT = r"""'(?:[sdmt]|ll|ve|re)| ?\p{L}+| ?\p{N}+| ?[^\s\p{L}\p{N}]+|\s+(?!\S)|\s+"""
```

| 规则                 | 含义                                                     | 示例                            |
| -------------------- | -------------------------------------------------------- | ------------------------------- |
| `'(?:[sdmt]          | ll                                                       | ve                              |
| ` ?\p{L}+`           | 连续字母，前面可以带一个普通空格                         | `"hello"`、`" world"`、`"你好"` |
| ` ?\p{N}+`           | 连续 Unicode 数字，前面可以带一个普通空格                | `"123"`、`" 456"`               |
| ` ?[^\s\p{L}\p{N}]+` | 连续的非空白、非字母、非数字字符，前面可以带一个普通空格 | `"-"`、`"!!!"`                  |
| `\s+(?!\S)`          | 匹配一段空白，但要求后面不能紧接非空白字符               | 处理末尾空白或连续空白的一部分  |
| `\s+`                | 匹配剩余的连续空白                                       | 制表符、换行等                  |

```
'(?:[sdmt]|ll|ve|re)
```

括号把所有后缀选项组成整体，含义是：

```
先匹配单引号，再匹配（s、d、m、t、ll、ve、re 中的一种）
```

其中 `?:` **不改变上述分组作用**，只是告诉程序：“这组内容不用额外单独保存。”

不用额外保存的是：**这对括号匹配到的那部分文本**。

比如用正则匹配 `"I'll"` 中的 `"'ll"`：

```
m = re.search(r"'(ll|ve|re)", "I'll")

m.group(0)  # "'ll"：整个正则匹配到的文本
m.group(1)  # "ll" ：第一对捕获括号匹配到的文本
```

普通括号 `(…)` 除了分组，还让你能通过 `group(1)` 单独取出 `"ll"`。

换成非捕获括号：

```
m = re.search(r"'(?:ll|ve|re)", "I'll")

m.group(0)  # "'ll"：整个匹配结果仍然存在
m.group(1)  # 报错：没有第一个捕获组
```

所以，**`(?:…)` 保留了括号的分组作用，但不提供单独提取括号内结果的编号。** 这里“不保存”指的就是这个，不是把匹配到的文本丢掉。



问题：(a) 分别采样 10 篇 TinyStories 和 OpenWebText 文档，各自分词器的压缩比是多少？

**写出正确版本不难，但写出比完整矩阵乘法更快的版本比较复杂。**

最直接的方式是逐个处理 query：第 \(i\) 个位置只与前 \(i+1\) 个 key 计算注意力。这样确实少算了上三角，但会产生许多小计算和循环开销，在 GPU 上反而可能更慢。

要高效实现，通常需要：

- **分块计算**：一次处理一组 query 和 key，保持 GPU 并行度。
- **跳过无效块**：整个块位于上三角时直接不计算，对角线附近的块再局部应用 mask。
- **处理 softmax 和中间结果**：尽量减少显存读写，同时保证数值稳定。

这里仍按 **batch size = 1、计算完整注意力矩阵、只统计矩阵乘法 FLOPs** 的口径计算。

##### **1. 固定模型参数，只改变序列长度**

GPT-2 XL 的配置保持不变：

\[ N=48,\quad D=1600,\quad F=4288,\quad V=50257 \]

分别表示层数、隐藏维度、FFN 中间维度和词表大小。序列长度从：

\[ S_{\text{old}}=1024 \quad\longrightarrow\quad S_{\text{new}}=16384=16S_{\text{old}}. \]

关键在于：不同矩阵乘法对序列长度的依赖不同。

##### **2. 投影运算随序列长度线性增长，因此增加 16 倍**

这些运算都是对每个 token 的向量分别做线性变换。token 数量增加 16 倍，运算量也增加 16 倍。

全模型中各部分的计算公式为：

| 组件                         | FLOPs 公式       |
| ---------------------------- | ---------------- |
| Q、K、V 投影与注意力输出投影 | \(N\times8SD^2\) |
| FFN 的三个投影               | \(N\times6SDF\)  |
| 语言模型输出头               | \(2SDV\)         |

例如，新的 FFN 计算量为：

\[ \begin{aligned} C_{\text{FFN}} &=48\times6\times16384\times1600\times4288\\ &=\boxed{32,373,315,993,600\text{ FLOPs}}. \end{aligned} \]

它正好是原来 \(2,023,332,249,600\) FLOPs 的 16 倍。

##### **3. 注意力的 \(QK^\mathsf{T}\) 和 \(AV\) 随序列长度平方增长，因此增加 256 倍**

每个头的 \(QK^\mathsf{T}\) 形状变化为：

\[ (S,d_k)\times(d_k,S)\rightarrow(S,S). \]

所有头合计的计算量为：

\[ 2HS^2d_k=2S^2D. \]

\(AV\) 的计算量相同，因此两个矩阵乘法在全部 48 层中的合计为：

\[ C_{\text{attention}}=N\times4S^2D. \]

序列长度增加 16 倍，这部分增加：

\[ 16^2=\boxed{256\text{ 倍}}. \]

代入新长度：

\[ \begin{aligned} C_{\text{attention}} &=48\times4\times16384^2\times1600\\ &=\boxed{82,463,372,083,200\text{ FLOPs}}. \end{aligned} \]

这里包含 \(QK^\mathsf{T}\) 和 \(AV\)，各占一半。

| 组件                        | 长度 1,024   | 长度 16,384    | 增长倍数        |
| --------------------------- | ------------ | -------------- | --------------- |

| \(QK^\mathsf{T}\) 与 \(AV\) | 0.322123     | 82.463372      | 256 倍          |
| FFN                         | 2.023332     | 32.373316      | 16 倍           |

| **总量**                    | **3.516770** | **133.577730** | **约 37.98 倍** |

新的总计算量为：

\[ \begin{aligned} C_{\text{new}} &=N(8SD^2+4S^2D+6SDF)+2SDV\\ &=16,106,127,360,000\\ &\quad+82,463,372,083,200\\ &\quad+32,373,315,993,600\\ &\quad+2,634,914,201,600\\ &=\boxed{133,577,729,638,400\text{ FLOPs}}. \end{aligned} \]

与原来相比：

\[ \frac{133,577,729,638,400}{3,516,769,894,400} \approx\boxed{37.98}. \]

占比用“该组件的 FLOPs ÷ 新的总 FLOPs”计算：

| 组件                        | 长度 1,024 时的占比 | 长度 16,384 时的占比 |
| --------------------------- | ------------------- | -------------------- |
| 注意力的四个投影            | 28.62%              | 12.06%               |
